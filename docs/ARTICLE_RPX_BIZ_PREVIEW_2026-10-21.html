7 份业务报表，逐格拆解：中国式报表真正的难点不在渲染

为什么从这 7 份开始

AI 报表引擎的样例库里有 29 份可运行报表，分成 11 个能力域。其中最大的一类叫典型业务报表，7 份——员工工资表、销售发货单、库存进销存台账、资金日记账、应收账款账龄分析表、利润表、资产负债表。

之所以先拆这 7 份，不是因为它们简单，恰恰相反：它们是最难被「通用报表工具」对付的一类。前面那些能力域——多源关联分片、不规则分组、交叉表合并——考验的是引擎的构造能力；而这 7 份考验的是另一件事：你做出来的东西，业务人员敢不敢拿去用。

  • 员工工资表——分组小计、逐行计算列，最日常的一份；
  • 销售发货单——单据式版式，要能直接打印交付；
  • 库存进销存台账——期初 + 入库 − 出库 = 期末，行内表达式；
  • 资金日记账——余额逐行结转，相对偏移引用；
  • 应收账款账龄分析表——条件汇总与区间边界；
  • 利润表——多级科目逐级汇总、两期对比；
  • 资产负债表——左右双栏，平衡校验差额必须是 0。

工资表要能直接发给员工，发货单要能打印出来交给客户，资产负债表左右两栏必须相等。这些要求跟「引擎能不能算」是两回事，但它们才是决定这套东西能不能上桌的东西。

这 7 份样例的另一个特点是：数据都是能读懂的。不是「字段 A 加字段 B」，而是「张伟基本工资 8000、奖金 3200、扣款 800，实发 10400」。你可以拿计算器核对，也可以拿自己公司的表对照。

每份样例都回答三个问题

7 份样例在画廊里都是同一个结构，每一份都在回答三个问题：业务上要什么、JSON 里怎么描述、断言验的是什么。前两个是给人的，第三个是给机器的。29 份样例一共带着 143 条这样的逐格断言，这 7 份贡献了其中 32 条。

数据不是编的，也不是引擎跑出来的

先说一件容易被误解的事：断言里的期望值不是引擎跑完记下来的日志，是人事先算好写进去的。

比如工资表，我们先在源数据里写下 6 个员工的部门、姓名、基本工资、奖金、扣款，然后手工算出每人实发是多少、合计是多少，把结果写进断言；引擎跑的时候必须逐个对上。如果期望值由引擎自己产生，那断言就只是引擎跟自己比，任何 bug 都会一起错，等于没验证。

本文里出现的每一个数字，我们都用源数据独立验算过一遍。你可以照着算，算出来的应该跟本文一致——不一致就是文章写错了，欢迎指出。

员工工资表 · 部门分组小计

先看最简单的一份，但它已经包含了中国式报表最常见的两个麻烦。画廊里的真实渲染：部门列纵向合并成一格，员工逐行展开，合计行由明细汇总，底部一行小字标注口径（同一份内分组内「部门」只出现一次并跨行覆盖；金额跳到千分位两位小数）。

部门姓名基本工资奖金扣款实发
销售部张伟8000320080010400
销售部李娜9000280095010850
销售部王强750015006008400
技术部陈晨120004000120014800
技术部刘洋110003500110013400
财务部赵敏9500200070010800

麻烦一：合并是显示层的事，不是数据层的事

「销售部」在页面上是一个跨 3 行的合并单元格，但如果你去问引擎「第 3 行的部门是什么」，答案必须是「销售部」，而不是空、也不是「同上」。

这条断言写得很直白：部门列逐行取值必须是 ["销售部", "销售部", "销售部", "技术部", "技术部", "财务部"]——六行六个值，一个都不能因为合并而少掉。在画廊的「运行校验」页里，这条断言连着员工列、实发列一起逐条展示，每条都标着模板原格坐标：

为什么这值得单独写一条断言？因为很多实现把合并做在了数据层：合并之后第 2、3 行的部门就真的没了。这样做出来的表看着对，但一旦你要按部门筛选、按部门做小计、或者导出成 Excel 让别人再加工，数据就断了。

麻烦二：计算列是逐行的，不是填公式

「实发」这一列，每一行都是 基本工资 + 奖金 − 扣款。它不是一个写死的数，也不是「Excel 里下拉填充」——它是一行表达式，数据来几行就自动算几行。

独立验算：张伟 8000 + 3200 − 800 = 10400，李娜 9000 + 2800 − 950 = 10850，王强 7500 + 1500 − 600 = 8400，陈晨 12000 + 4000 − 1200 = 14800，刘洋 11000 + 3500 − 1100 = 13400，赵敏 9500 + 2000 − 700 = 10800。六行与断言逐条一致。

合计行是另一套口径：基本工资合计 57000（8000+9000+7500+12000+11000+9500），实发合计 68650（10400+10850+8400+14800+13400+10800）。两者都由明细汇总，不是另写一遍公式——这样改任何一个明细，两处合计都会跟着变。

销售发货单 · 一单多行明细

这份样例把报表推到了交付形态：抬头带客户与单号，下面是多行商品明细，底部是金额合计、税额、价税合计和签收栏。一张纸可以直接打印出来交给客户。

行品名数量单价（元）金额（元）
1工业铝型材 4040120168.0020160
2角件 404048012.506000
3直线导轨 HGR2036265.009540
4滚珠丝杆 SFU160524398.009552
5伺服电机 750W121860.0022320
6联轴器 8×102486.002064
金额合计（不含税）69636
增值税 13%9052.68
价税合计78688.68

金额 = 数量 × 单价，逐行算

六行明细的金额都是数量乘单价：120 × 168 = 20160、480 × 12.5 = 6000、36 × 265 = 9540、24 × 398 = 9552、12 × 1860 = 22320、24 × 86 = 2064。全部与断言逐条一致。

合计 69636 = 20160 + 6000 + 9540 + 9552 + 22320 + 2064，独立验算一致。

税额是乘出来的，不是抄来的

13% 增值税：69636 × 0.13 = 9052.68；价税合计 69636 + 9052.68 = 78688.68。两个数字都由合计推导，不是手填常量。

这一点在实际业务里很关键：税率会变。如果税额是写死的，改一次税率就要改所有单据模板；如果税额是从合计算出来的，改一处就够。

单据式版式是另一种要求

注意这份样例不只是「算得对」，还要求版式对：抬头、明细区、合计区、签字栏各在其位，打印出来是一张完整的单据。这跟「能不能算」是两套能力，但少了它，做出来的东西就只能内部看，交不出去。

库存进销存台账

仓储月度台账，规则一句话就能说完：期初 + 入库 − 出库 = 期末。但就是这么简单的一句话，实现方式差别很大。

编码品名期初入库出库期末
A-1001碳钢法兰 DN50120300260160
A-1002不锈钢球阀 DN256418015094
A-1003橡胶垫片 DN5090012001500600
A-1004六角螺栓 M12451209075
A-1005轴承 6204-2RS28607216
A-1006液压油 46#12242016
合计18842092

期末是同一行的表达式结果

「期末」这一列不是从数据库查出来的字段，而是同一行里期初、入库、出库三个字段的表达式结果。逐行验算：120+300−260 = 160，64+180−150 = 94，900+1200−1500 = 600，45+120−90 = 75，28+60−72 = 16，12+24−20 = 16。六行与断言 [160, 94, 600, 75, 16, 16] 完全一致。

注意 A-1005 和 A-1006 的期末都是 16，但一个是 28+60−72、另一个是 12+24−20——数字相同不代表算法相同，断言逐行钉死才能区分这两种情况。

数量与金额混排在同一张表

入库合计 1884、出库合计 2092 是数量；入库金额合计 15900 是金额（5400+6300+360+720+1440+1680）。同一行里既有数量列又有金额列，两者的汇总口径不同但互不相扰——这也是中国式台账的常见形态。

资金日记账 · 逐行结转

出纳日记账，规则同样只有一句：每行余额 = 上一行余额 + 借方 − 贷方，首行还要加上期初余额。

日期摘要借方贷方余额
2025-09-02收到华东机械集团货款3200000448500
2025-09-03支付原材料采购款0186000262500
2025-09-05支付职工薪酬0142000120500
2025-09-08收到华南建材预收款960000216500
2025-09-10支付水电费018600197900
2025-09-12支付差旅报销032400165500
2025-09-15收到西部电力货款2100000375500
2025-09-18缴纳增值税052400323100
本期合计626000431400323100

相对偏移引用：余额要能指向上一行

关键在「上一行」这三个字。余额这一格的表达式要引用它自己上一行的同一列，这种引用方式叫相对偏移引用。数据多一行少一行，引用关系自动跟着走，不需要改模板。

逐行验算（期初余额 128500）：128500 + 320000 = 448500；448500 − 186000 = 262500；262500 − 142000 = 120500；120500 + 96000 = 216500；216500 − 18600 = 197900；197900 − 32400 = 165500；165500 + 210000 = 375500；375500 − 52400 = 323100。八行与断言逐条一致。

期初值放在宏里

期初余额 128500 不是硬编码在某一格里，而是放在宏里。换个账户、换个期间，改一处即可。硬编码期初值的后果是：每换一个账户就要复制一份模板，改的时候还要记得改所有副本。

两个独立算法必须殊途同归

这份样例有一条断言特别值得单独说：「期末余额与最后一行一致」。

期末余额可以用两种方式算出来：一种是逐行结转（一路加加减减到最后一行），另一种是期初 + 借方合计 − 贷方合计（128500 + 626000 − 431400 = 323100）。这是两条完全不同的路径，但结果必须相等。

如果它们不相等，说明至少有一处算错了——而这类错误不会报错，只会让账面慢慢对不上。把两条路径都写成断言，等于给同一件事上了两把锁。

应收账款账龄分析表

按客户逐行统计各账龄区间的金额。规则看着简单，但里面藏着一个最容易写错的边界。

客户应收余额账龄天数90 天以上
华东机械集团1286000180
华南建材742000520
北方重工48600096486000
西部电力31800070
长三角汽配264000740
中原化工156000135156000
合计3252000642000

每个区间列都是两个条件的汇总

「90 天以上」这一列不是简单的筛选，而是「当前客户」+「天数 > 90」两个条件同时成立时的汇总。少一个条件，就会把别人的账算到这个客户头上。

边界：74 天不算 90 天以上

看长三角汽配这一行：账龄 74 天，90 天以上列是 0。这是刻意放进来的一条边界数据。

为什么值得写进断言？因为账龄分段的边界写法很多：> 90、>= 90、>= 91，还有按「区间左闭右开」实现的。这些写法在 74 天这种明显不达标的数据上结果都一样，只有在边界附近才会分出对错。样例里同时放了 74 天（不该计入）和 96 天、135 天（该计入），就是为了让错误实现暴露出来。

合计验算：应收总额 3252000 = 1286000+742000+486000+318000+264000+156000；90 天以上合计 642000 = 486000+156000，占总额 19.74%。两个数字独立验算与断言一致。

利润表 · 本期与上期对比

标准财务报表版式：从营业收入逐级算到净利润，本期与上期两列由同一科目口径汇总，变动率按行计算，三级缩进体现科目层级。

科目本期上期
营业收入28600002540000
营业成本17460001580000
税金及附加4280038600
销售费用196000178000
管理费用164000152000
研发费用9800086000
财务费用2600024000
其他收益1800012000
营业利润605200
营业外收入 / 支出6000 / 40004000 / 3000
利润总额607200
所得税费用10800086000
净利润499200408400

逐级汇总：每一级都引用上一级

营业利润不是单独配置的，而是由上面的科目一级一级引用算出来的：

2860000 − 1746000 − 42800 − 196000 − 164000 − 98000 − 26000 + 18000 = 605200。

接着：利润总额 = 营业利润 + 营业外收入 − 营业外支出 = 605200 + 6000 − 4000 = 607200；净利润 = 利润总额 − 所得税费用 = 607200 − 108000 = 499200。三级结果与断言逐条一致。

两期对比：上期也要能独立算对

上期那一列同样要走一遍完整链路：2540000 − 1580000 − 38600 − 178000 − 152000 − 86000 − 24000 + 12000 = 493400（上期营业利润）；+ 4000 − 3000 = 494400（上期利润总额）；− 86000 = 408400（上期净利润）。与断言一致。

变动率按行计算：净利润较上期增长 22.23%（(499200 − 408400) ÷ 408400）。

这里有个容易被忽略的点：两期必须由同一套科目口径汇总。如果本期改了科目层级、上期没跟着改，两列就不可比，变动率算出来也是假的。

资产负债表 · 左右双栏

最后一份是压轴的：一张 A4 上并排两栏，左栏资产、右栏负债和所有者权益，各自一列期末、一列年初，底部给出平衡校验差额。

左右各自独立汇总

资产侧 9 个科目：货币资金 1286400、应收账款 862000、存货 748600、其他流动资产 96000、固定资产 1420000、在建工程 260000、无形资产 158000、长期待摊费用 42000、递延所得税资产 30000，合计 4903000。

负债与所有者权益侧 9 个科目：短期借款 600000、应付账款 748000、应付职工薪酬 186000、应交税费 96000、其他应付款 74000、长期借款 800000、实收资本 2000000、资本公积 120000、未分配利润 279000，合计 4903000。

平衡校验差额必须等于 0

这是整份样例最硬的一条断言：「平衡校验差额 · 期末」= 0。

它不是「两边都算出 4903000 所以相等」这种自欺欺人的写法，而是真的做了一次减法并把结果钉死为 0。这意味着：只要资产侧或负债侧有任何一个科目算错、漏算、重复算，这个差额就不是 0，样例立即失败。

独立验算：资产侧逐项相加 = 4903000，负债权益侧逐项相加 = 4903000，差额 = 0。两侧各 9 个科目，没有一个被漏掉。

这就是为什么财务报表是最好的测试用例——它自带一个不需要额外设计的正确性判据。你不用想「正确答案是什么」，答案就是 0。

七份放一起看：中国式报表的四个共同难点

单独看每一份，规则都不复杂。但七份放一起，会浮现出四个反复出现的要求——它们才是中国式报表真正的难点。

  • 合并是显示层的事，数据不能断——工资表的部门列合并了，但引擎逐行取值仍要拿到六个「销售部」；
  • 计算要能引用「上一行」「上一格」——日记账的余额、进销存的期末、利润表的逐级汇总，都依赖相对位置的引用；
  • 同一个数要有两条独立路径算得出——日记账期末余额的两条算法、资产负债表两栏各自汇总，互为校验；
  • 边界必须被单独钉死——74 天不算 90 天以上，这种边界数据要刻意放进样例，否则错误实现暴露不出来。

难点一：合并是显示层的事，数据不能断

工资表的部门列要合并成跨行单元格，但数据层必须保留六行六个「销售部」。显示可以合并，数据不能合并——否则筛选、小计、导出全部失效。

难点二：计算要能引用「上一行」「上一格」

日记账的余额引用上一行同一列，进销存的期末引用同一行的其他字段，利润表的营业利润引用上面多个科目。这些引用必须随数据行数自动跟随，不能写死行号。

难点三：同一个数要有两条独立路径算得出

日记账的期末余额，逐行结转是一个答案，期初加借贷合计是另一个答案；资产负债表两栏各自汇总，减出来必须是 0。两条路径对不上，说明有地方错了——而这类错误不报错，只会让账面慢慢失真。

难点四：边界必须被单独钉死

账龄表里 74 天不计入 90 天以上，96 天计入。边界数据要刻意放进样例，否则正确实现和错误实现在大部分数据上表现一致，只有到边界才分出对错。

怎么拿到并运行这些样例

这 7 份（以及全部 29 份）都是可运行的，不是截图。三条路都可以走通。

用 CLI 跑一份

最轻的一条路，装好 CLI 之后两步走：先静态检查，再真正执行导出。这条链路是给自动化和 Agent用的——命令默认输出 JSON，方便程序消费。

rpx lint examples/r-model/payroll.json --data-dir examples/r-model
rpx run  examples/r-model/payroll.json --out-dir /tmp/out --export xlsx
  • rpx lint：静态检查，拦截「不报错但产物错」的写法；--strict 时 warning 也返回非零退出码，可当 CI 闸门用；
  • rpx run：真正执行，--export 可选 csv / xlsx / print-xlsx / html / pdf；
  • rpx doctor：环境与能力自检，不确定环境是否就绪先跑它；
  • rpx capabilities：返回引擎的自描述——命令面、导出格式、限制、错误码，Agent 无需读文档就能接上。

然后用 rpx-server serve --library … 起服务，打开 /gallery.html，深链格式是 /gallery.html#<报表 id>——比如本文的工资表就是 #payroll。

想要源码与数据

每一份样例都包含三样东西：一份 JSON 模板定义、一份 CSV 源数据、一组逐格断言。断言写在 catalog.json 里，跟模板分开存放——这样才能保证期望值不是引擎自己算出来的。

常见问题

这些数字是真实的吗？

是自洽的演示数据，不是某家公司的真账。但每一份都按真实业务规则构造：工资表的实发公式、发货单的 13% 税率、账龄的 90 天分界、资产负债表的平衡关系，都是照着实际做法来的。你可以把自己公司的 CSV 换进去跑同一份模板。

为什么断言里会出现 0？

比如账龄表 90 天以上列有好几个 0，资产负债表的差额是 0。「这里是 0」和「这里没算」是两回事——前者是正确答案，后者是 bug。把 0 写成断言，才能区分这两种情况。

29 份里另外 22 份是什么？

另外 10 个能力域，包括多源关联分片（3 份）、自由格间运算（5 份）、交叉表合并（3 份）、统计图与图形（4 份）、不规则分组（2 份）、多口径分组合计、行列对称、混合数据源、条码与标签、表单与序号列。它们考验的是引擎的构造能力，另一篇文章专门讲这些样例的断言机制。

我能改这些样例吗？

可以，而且建议改。每份样例都是一份 JSON 定义加一份 CSV，改完再跑一遍 rpx lint 和 rpx run，断言会告诉你改坏了没有。这也是这套样例最主要的用途：不是给你看结果，是让你改的时候有安全网。

引擎是怎么保证换语言不换语义的？

这套引擎是 Rust 重写的，重写过程中靠的正是这类夹具对拍。这篇文章讲了为什么这么做、换来了什么；这篇讲扩展格这个核心算法。
