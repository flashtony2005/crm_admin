一、项目现状一句话盘点

已经建成一个"骨架完整、外围铺得宽"的轻量 CMS：后端 Rust/Axum + SQLite 约 7000 行、27 个模块；前端 React 19 + HeroUI v3 + TanStack，PC 管理中心 + m.tsx 移动端双形态。Phase 1（内容地基）完成度高，Phase 2–4 的能力（AI 执行器、审批、Newsletter/会员、Webhook、Automation）已有代码骨架。

能力域已落地成熟度
内容与站点文章/页面通用 CRUD 网关（resources.rs）、slug/tag/JSON-LD、站点主题/模板（templates.rs，未提交）、导航与主页置顶（nav_links/home_pins）、公开只读 API较完整
权限与安全perm.rs 权限矩阵 + 前端镜像、AI Capability→Policy→Approval→Audit 全链路、ai_audit_log较完整
公开站消费端SEO 端点、四套主题、作者页/标签页/表单公开路由可用
获客侧公开表单、会员（members）、Newsletter、订阅（subscriptions）、审批通知（notify）有骨架、缺闭环
AIai.rs 执行器（能力注册表 + 策略拦截 + 审批升级 + 审计）只有"手"，没有"脑"
自动化automation.rs、scheduler.rs、webhooks_out.rs骨架

二、第一性原理：这个产品到底要解决什么

回到 PRODUCT_VISION 的最终一句话："让小企业老板用自然语言管理网站、内容、客户和日常运营，AI 干活但权限可控。"剥掉所有技术栈，小企业的实际需求本质上是一条价值链：

把内容发上网→ 被人搜到→ 访客变线索→ AI 替人干活→ 老板可控可审计→ 便宜好维护
本质需求支持能力评估评分
① 老板/员工能把内容发到网上，访客能看到像样的站点 编辑器、主题、导航、置顶、公开 API、SEO 全都有，且刚迭代完 UX 细节。这是目前做得最好的一环。
85%
② 内容能被搜索引擎找到 slug、tag 聚合、JSON-LD、SEO 端点已落地；缺 sitemap.xml 自动生成与 robots 管理。
70%
③ 访客变线索（表单→线索→跟进） public_forms / members / subscriptions 各自存在，但没有一条"提交→进线索池→通知→跟进状态"的完整闭环，三个模块互相不通。
35%
④ 老板用自然语言让 AI 做事（产品核心竞争力） ai.rs 是一个安全的执行器（capability 注册 + 策略 + 审批 + 审计），但没有接任何真实 LLM 编排层——前端 pi-agent 目录只有 types.ts。"自然语言 → 意图 → capability 调用"这条最关键的链路不存在。
20%
⑤ AI 不越权、事后可追责 权限矩阵 + Policy 拦截 + 审批升级 + ai_audit_log，链路设计到位且已实现。这是项目的第二大亮点。
80%
⑥ 低成本自托管、好维护 单二进制 + SQLite 文件，成本面优秀。但交付工程未定型：cms_live.db 直接进 git、无版本化迁移、无备份策略、无一键部署，编译还强依赖本机环境。
45%

三、核心结论：最大的错配

产品定位的第一性原理是"AI 替人干活"，而过去几个月约 80% 的实际工作量花在了传统 CMS 功能上（主题、模板、导航、置顶、UX 细节）。AI 只有一个安全壳子（执行器），没有大脑（LLM 编排）。
照这个路径继续走，三个月后得到的会是一个"不错的自托管 Ghost 平替"，而不是产品纲领里定义的差异化产品。当前必须做一次方向校正：要么把 AI 大脑补上，要么坦率把产品定位收缩为"轻量自托管 CMS"。

四、具体不足清单（按优先级）

P0 · 动摇定位

  • AI 主入口名不副实：没有 LLM 接入层，没有"自然语言 → tool call → /api/ai/invoke"的编排。assistant.tsx 空有界面。web/src/pi-agent/ 仅 types.ts。
  • 交付工程未定型：cms_live.db（运行时库）被纳入 git，二进制污染仓库且随时会冲突；无 sea-orm-migration/refinery 版本化迁移；无备份/恢复脚本；部署依赖"本机 cargo build + 手动跑 exe"。
  • 工作区漂移风险：templates.rs、perm.rs、site.rs 等 10+ 文件未提交，最新能力（站点模板）只存在于工作区，一旦误操作即丢失。

P1 · 需求链断裂点

  • 线索闭环缺失：public_forms 提交后没有进入统一的 leads 池，不触发通知，无跟进状态机——价值链在第 3 环断掉。
  • G1"5 分钟行业初始化"未启动：templates.rs 有站点模板底子，但没有任何行业模板，新用户仍是空白站点起步。
  • 搜索能力：SQLite LIKE 匹配，文章量上千后体验劣化；FTS5 是零基础设施成本的标准解。
  • 移动端审批推送：Phase 3 验收项"手机收到审批推送一键批准"目前靠轮询，无 PWA push。

P2 · 打磨项

  • 内容版本（Version）记录仍是验收清单未勾选项，误删/误改无法回滚。
  • 审计有日志无界面深度（按 capability/actor 的聚合视图）。
  • 文档存在 3 份不同日期的 status HTML，信息已开始漂移，缺单一 status 来源。
  • 无 CI：tests_api.rs 存在但没有自动跑的环境，Rust 侧验证完全依赖本机。

五、改进路线（建议顺序）

① 提交工作区
消除漂移→ ② 定型交付
迁移/备份/一键启动→ ③ 补 AI 大脑
LLM→capability→ ④ 线索闭环
form→lead→通知→ ⑤ 1 个行业模板
验证 G1
#动作要点
1git 提交 + 仓库瘦身先提交全部未提交工作；随后把 cms.db/cms_live.db 移出 git（.gitignore + 保留一份结构种子 db）。
2定型交付链引入 sea-orm-migration 管理建表（替换 db.rs 内散落的 CREATE TABLE IF NOT EXISTS）；scripts/ 增加 backup.ps1（sqlite .backup + 按日期留存）；提供一键 dev 启动脚本。
3补 AI 大脑（最高价值）后端加一个 LLM provider 模块（可配置 OpenAI 兼容 API），实现：自然语言 → LLM function-call → 映射到已有 /api/ai/invoke 的 capability 注册表 → 结果回填对话。安全链路（Policy/Approval/Audit）一行不用改——这正是现有设计的红利：大脑可以慢慢换，手脚已经合规。
4线索闭环新增 leads 表（或复用 members 扩展 status 字段）：public_forms 提交 → 写入 lead → notify 通知 → 后台「Business/Leads」看板，状态：新/跟进中/已转化/已流失。
5第一个行业模板选一个最熟的行业（如本地服务），用 templates.rs + site_settings 打包：页面结构 + 导航 + 表单 + 首页置顶预设，验证"5 分钟初始化"可行性。
6P2 顺带FTS5 全文索引、sitemap.xml 自动生成、文章版本表、审计聚合视图、GitHub Actions 跑 cargo test（Rust 侧即使沙箱受限也可推到远端 CI 跑）。

六、总结

做对了的：技术选型克制（SQLite/单二进制，没提前上 Redis/K8s）；权限与 AI 安全链路是真材实料的设计资产；公开站点消费端完整度超预期。

要警惕的：项目正在"舒适区滑行"——不断打磨 CMS 外围细节（置顶、排序、加载态），而产品灵魂（AI 执行）停在 20%。外围功能再多，也只是 Ghost 的平替；AI 大脑接上，才是纲领里那个产品。

下一步最小动作：① 提交当前工作区 → ② 后端新增 llm.rs 接一个 OpenAI 兼容端点，打通"顶栏输入框 → 生成一篇文章草稿 → 走审批 → 发布"这一条完整演示链。这一条链跑通，产品定位才算成立。
