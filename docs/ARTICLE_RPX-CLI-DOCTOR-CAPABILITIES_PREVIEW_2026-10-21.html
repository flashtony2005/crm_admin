不读文档也能接上：rpx capabilities 与 doctor 的自描述设计

为什么 CLI 要先会自述

报表引擎的 CLI 有个不太常见的设计：它把自己能干什么、会怎么失败、边界在哪，全部作为一条命令的输出返回，而不是写在文档里等你去读。

rpx capabilities
rpx doctor

本文是 CLI 系列的第一篇，其余四篇分别讲静态检查、执行与导出、模板的查看与补丁、目录库与生命周期。

这两条命令都不需要数据、不需要网络、不需要鉴权——offline: true、authentication: "not_required"。它们是给程序准备的：一个 Agent 拿到 capabilities 的输出，就知道有哪些命令、参数怎么传、失败会长什么样，不需要先去啃一份人类文档。

这不是偷懒省文档，而是把「文档会过期」这个问题从根上绕开：输出是代码当场生成的，不会和实现对不上。当然，前提是你真的把每一项都从实现里取——本文后面会讲一处没做到的地方。

capabilities：一张清单顶一份文档

输出是一个 JSON，我们按用途拆成五块看。

一、命令面：26 条，每条带一句话摘要

实测当前版本（0.16.0，protocol_version: 1）返回 26 条命令，每条有 name / summary / offline。按职责大致分五组：

  • 自述与自检：doctor、capabilities、schema.template
  • 定义面：template.inspect、template.validate、template.create、template.patch、lint
  • 执行与产物：run、result.inspect
  • 数据面：dataset.inspect、catalog.functions、catalog.examples
  • 目录库：library.init 加 report.* 共 12 条（list / show / runs / copy / patch / validate / run / update / import-json / delete / migrate / prune）

二、错误码：32 个，每个带退出码与阶段

这是我认为最实用的一块。32 个错误码，每个都给了 code / exit / meaning / stage，部分还标了 hint: true（表示错误信息里会附带可执行的提示）。

退出码是分层的，而且分层方式对自动化很关键：

退出码含义该不该重试
0成功（可能带 warning 诊断）—
2用法/参数错误不重试，重试同样参数无用
3定义错误（JSON 不合法、表达式语法错、结构冲突）改模板后再试
4输入/数据错误（文件缺失、列不存在、连不上库）修输入后再试
5计算错误（表达式求值失败）多为作用域/列引用问题
6IO/导出/内部错误看具体诊断

「2 不重试」这一条看着简单，实际能省掉大量无效循环：Agent 最常见的坏行为就是拿到参数错误后换个姿势再试八次。

三、限制值：这些是硬边界，不是建议

项值
Excel 最大列数16384
Excel 最大行数1048576
分页每页上限500
SQL 结果默认行数100000（可用 RPX_SQL_MAX_ROWS 覆盖）

把它们放进自述而不是文档，是因为它们会变。程序读的是当场的值，人读文档可能读到上一版。

四、约定（conventions）：四条容易踩的口径

这一块是纯经验，读一遍能省掉几次调试：

  • border：模板可声明，但当前导出不落地——写了等于没写；
  • 坐标从 1 起，A1 风格——不是 0 起；
  • 同排多个 vertical 必须用 left_head 串父子链——否则扩展相乘；
  • 宏只在 expr 里替换，写进 text 会原样上屏。

五、数据源与导出

datasources 列出 6 种：CSV、TSV、Excel、SQLite、PostgreSQL、MySQL。exports 列出 5 种：csv、xlsx、print-xlsx、html、pdf。

doctor：当前环境到底能跑什么

capabilities 说的是「引擎支持什么」，doctor 说的是「这台机器上现在能用什么」。两者的区别很重要。

binary：版本是否与源码一致

实测输出里有一项 binary，带 version、source_version、source_manifest、stale：它拿可执行文件的版本和源码 Cargo.toml 比对，stale: true 就意味着你跑的二进制比源码旧。这在「改了引擎却忘了重编 CLI」时非常有用——症状往往是莫名其妙的行为差异，很难往版本上想。

pdf：有没有可用的浏览器

PDF 导出走 chrome-headless，所以能不能用取决于机器上有没有浏览器。实测这台机器：

"available": false,
"detail": "未找到 Chrome/Chromium/Edge；--export pdf 不可用，可设 RPX_CHROME 指定浏览器路径"

注意它没有把这条算作失败——ok: true。这是有意的：缺浏览器不影响其他 4 种导出，不该让整个自检红掉。真正的失败会在你真的请求 pdf 时以 warning 形式出现。

library / datasources：按需才查

这两项默认显示 "not requested"。要查就显式传参：

rpx doctor --library /path/to/lib
rpx doctor --datasources /path/to/datasources.json

一个不一致：5 种导出 vs 3 种

把两条命令的输出放在一起看，会发现一处对不上：

来源exports
capabilitiescsv、xlsx、print-xlsx、html、pdf（5 种）
doctorcsv、xlsx、print-xlsx（3 种）
run --export 参数接受 5 种

我核对了实现：run 确实实现了全部 5 种——html 和 pdf 都先渲染成页面，pdf 再交给 Chrome。所以 capabilities 是对的，doctor 那份列表是硬编码的常量，没跟着更新。

这类不一致正是「自描述」要防的东西，而它恰恰在自描述里漏了一处。用法上的结论是：想知道当前能导出什么，以 doctor 为准；想知道一共支持什么，以 capabilities 为准——但在修好之前，更稳的做法是直接请求你要的格式，然后看返回的诊断。

顺带说一句：REVISION_CONFLICT 也是同样情况——它是目录库写入时真实会返回的错误码，但不在 capabilities 的 32 条清单里。

Agent 的接入回路

把这两条命令用起来，一个最小但完整的回路是这样的：

  1. 先 rpx doctor：确认版本没过期、pdf 可不可用、数据源通不通；
  2. 再 rpx capabilities：拿到命令面、错误码表、限制值，之后所有调用都按这张表来；
  3. 写定义 → rpx lint：静态自检；
  4. rpx run：真跑，看 diagnostics 而不是只看 ok；
  5. 失败时按退出码分层处理：2 不重试，3 改定义，4 修输入，5 查引用。

第 4 步那句「看 diagnostics」值得强调：一次 run 可以 ok: true 但带着 warning（比如某个导出格式失败了）。只看 ok 会漏掉这些信息——这篇里有实测的完整返回。

常见问题

输出太长，能只看人话吗？

可以。所有命令都支持 --output text，全局参数，默认 json。程序用 json，人看 text。

它需要联网吗？

不需要。offline: true 是写在自述里的，全部命令都不依赖网络（连数据源也是本地文件或你自己的库）。

web_executes_engine: false 是什么意思？

意思是网页端不执行计算。引擎的 HTTP 服务只伺服固定产物，不做实时求值；要算就得走 CLI 或库。这也是为什么样例画廊是预先生成好的。这篇讲了这个取舍。

版本会变，我要锁死吗？

protocol_version 就是为这个准备的：它是输出结构的版本，和 version（引擎版本）分开。结构不兼容时 protocol_version 会变，程序应该先看这个字段再解析。
