报表引擎是企业软件里最“重”的那一环。它要把数据、公式、版式、分页、导出全部揉在一起，还要面对财务、保险、烟草、制造、政务这些行业里几十年沉淀下来的“中国式复杂报表”。过去十年，这类引擎大多长在 JVM 上：功能齐全，但部署重、启动慢、行为难以测试。

我们把一套成熟的 Java 报表引擎重写成 Rust。这篇讲三件事：为什么重写、怎么保证“换语言不换语义”、以及今天它长成了什么样。

一、旧架构的三个真实痛点

部署重。一个报表服务要带 JVM、一堆 JAR、字体、模板目录；容器镜像动辄几百 MB，客户内网升级时要先协调 JDK 版本。

启动与内存不可控。JVM 需要预热，冷启动与峰值内存取决于 GC 策略；在“一次请求渲染一张报表”的边缘场景里，这部分开销并不便宜。

行为难以钉住。报表引擎的输出是“一张网格”——行列位置、合并、扩展、分页、格式都要逐格一致。传统做法靠人工比对，回归成本高，改动容易悄悄破坏旧模板。

二、重写原则：行为对拍，不重造语义

我们没有把“重写”理解成“重新设计”。相反，第一原则是以原产品的实际输出为唯一判据：同一份模板、同一份数据，新旧引擎的网格必须逐格一致。

  • 夹具优先。每个能力点先固定一份可复现的样例（模板 + 数据 + 期望网格），实现围绕夹具收敛。
  • 裁决顺序固定。夹具 > 源码 > 契约文档 > 使用手册。文档与实现冲突时，以可执行证据为准。
  • 变异测试。关键判据要能被“故意改坏”检出；只报通过、不报证据的测试不算数。

换语言不是目的，把“中国式报表”的语义变成可执行、可验证的定义才是。

三、新架构：一条从定义到交付的流水线

重写后的引擎按职责拆成几层，依赖方向单向向下：

层职责关键约束
rpx-model报表定义模型、读写零第三方依赖
rpx-engine表达式、扩展算法、计算、合并、分页零第三方依赖
rpx-dsSQL / Excel / CSV 数据源连接由调用方注册
rpx-exportExcel / HTML / PDF 导出只吃算完的网格
rpx-runtime把定义 + 数据跑成结果统一执行入口
rpx-cli / rpx-server命令行与 HTTP 接口薄适配层

这条流水线的输入是一份 JSON 定义：数据集、公式、扩展方向、样式、打印设置都在里面。输出可以是网格快照、Excel、HTML 或 PDF。同一份定义，在 CLI、HTTP 服务和 Agent 里走的是同一条执行链。

四、换来了什么

  • 单二进制部署。没有 JVM、没有 JAR 地狱；一个可执行文件加模板与数据源配置即可运行。
  • 冷启动无预热。进程起来即可服务，适合容器弹性伸缩与边缘部署。
  • 确定性输出。同一输入得到同一网格；排序、合并、分页都可复现，回归可以机器判。
  • 可嵌入。引擎是库，不是“只能通过产品界面使用”的黑盒；CLI、HTTP、Agent 都能直接调。

更重要的是，回归从“人眼看”变成了“夹具对拍”。今天仓库里 20+ 份样例覆盖多源分片、不规则分组、自由格间运算、交叉表合并、统计图、条码与典型财务报表；每次改动都要过同一套机器闸。

五、它不是什么

它不是“重写一遍 Excel”。Excel 是通用电子表格，而报表引擎解决的是“模板 + 数据 → 可交付报表”：扩展、分组、合并、分页、导出，每一件都要在语义层做对。把这些语义做成一份可执行的定义，才是这次重写真正的产出。
