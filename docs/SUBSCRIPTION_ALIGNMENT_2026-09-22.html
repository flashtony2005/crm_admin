现有项目与「Rust SaaS 订阅架构」方案的对齐分析

对象：F:\project\admin（admin CMS + CouCouYa 主页）　·　比对基准：《Axum + SQLx + PostgreSQL + Rauthy + Stripe 托管收银台》方案（核验日 2026-09-21）　·　分析日 2026-09-22　·　结论基于源码实测，非文档推断
一句话结论：这份方案有两个层次——「订阅可靠性语义」与「具体技术栈选型」。前者你必须在对齐清单里补齐，后者大部分不该对齐：方案写给的是一个 1–3 人出海工具站，而当前项目是私有化交付、单实例、国内微信生态为主的创作者变现站，把 Rauthy / PostgreSQL / Askama 搬进来会与既有交付形态直接冲突。

更重要的发现：真正卡住你的不是"缺什么功能"，而是现网已有 1 个资损级越权洞 + 1 条近乎裸奔的 Stripe 链路；同时同项目里的微信支付链路反而比 Stripe 链路成熟一个数量级，方案要求的 outbox、指数退避、原子幂等、金额校验，你在微信侧和出站 Webhook 侧其实已经做完了。

两条收款链路的成熟度差了一个数量级

这是本次分析最值得注意的结构性事实：你为国内主渠道（微信）建了完整的资金安全体系，但 Stripe 那条路几乎是 demo 骨架。对齐工作应当"先把 Stripe 拉到微信的水平"，而不是"整体换架构"。

3P0：现在就存在的缺陷（不是"缺功能"）

P0 资损任何注册会员可自助把套餐改成 pro，零成本解锁全部订阅内容

会员自助资料接口把 plan 当成可写字段，而付费墙判定只读这个字段：

main.rs:171　POST /api/public/members/me → members::update_me

members.rs:252-272　MemberUpdate { name, plan } — 客户端传 plan 即写入 members.plan

public_api.rs:112-124　subscribed() = plan != 'free' && (plan_expires_at 为空 → 视为有效)

链路完整成立：注册（默认开放，member_invite_required=off）→ POST /api/public/members/me {"plan":"pro"} → paid_level=1 文章全文解锁。且 plan_expires_at 为空被当作不限期，等于永久会员。

诚实说明：分析时 8088 未运行，未做端到端实测；以上为源码路径推演，建议你本机起服务后一条 curl 复核。

修法：从 MemberUpdate 删掉 plan 字段，update_me 只允许改 name。plan 的唯一合法写入口 = 订单确认发货 / 兑码核销 / 后台改。顺带把「plan_expires_at 解析失败视为不限期」改成拒绝（安全默认）。
P0 资损Stripe 未配置时会静默发放会员
subscriptions.rs:98-107　match STRIPE_SECRET_KEY → 缺失或 tier 无 price_id 时进入 else 分支

该分支直接把 members.plan 置为 tier_slug 并 status=1，然后返回一个 ?demo=1 的成功页。生产环境漏配一个环境变量，任何登录用户点一下"购买"就白拿会员——这正是方案中"支付成功页不能直接授予权益"的反面案例。

修法：改为「未配置即拒绝（返回明确错误）」，演示模式必须由显式 STRIPE_DEMO_MODE=1 且 CMS_ENV != production 同时满足才生效。
P0 丢单Stripe Webhook 处理失败仍返回 2xx，事件无痕丢失
subscriptions.rs:112-141　stripe_webhook
  • 事件不落库：没有 event_id 去重，Stripe 按官方策略重发时会被重复执行；
  • DB 更新用 .ok() 吞掉错误，仍返回 {"received": true} → Stripe 认为投递成功，不再重试，用户付了钱但系统永远不知道；
  • 只处理 checkout.session.completed：续费成功、续费失败（invoice.payment_failed）、取消、退款全部无人处理；
  • 验签无时间戳容差（未校验 t= 与当前时间差），存在重放窗口。
修法（照微信链路的成熟做法对齐）：① 先建 webhook_events(event_id UNIQUE, type, payload, status, attempts)；② INSERT 冲突即视为已处理，直接返 2xx；③ 入库成功才返 2xx，处理失败返 5xx 交给上游重试；④ 补 subscription.updated/deleted、invoice.payment_succeeded/failed 分支；⑤ 验签加 5 分钟时间容差。
P0 越权会员 Token 无法撤销：封禁后仍可用最长 30 天
members.rs:24-45　MemberAuth 提取器只验签，不回查 members.status

members.rs:55　会员 token exp = now + 30 天，且 tv 固定为 0（不参与版本校验）

管理员侧已经修过这个问题（auth.rs:157-171 逐请求回查 users.status 与 token_version），会员侧没有对应实现。后果：封禁违规会员、改密、踢下线后，旧 token 在其有效期内依然能读付费内容和改资料，方案中"封禁用户时同时撤销业务 Session"未达成。

修法：在 MemberAuth 里照抄管理员侧做法——查 SELECT status, plan, plan_expires_at FROM members WHERE id=?，status != 1 直接 401。顺带把 plan 判定也一并带进来，避免每次请求二次查库。

4P1：订阅语义缺口（方案的核心内容）

这一层不是"有 bug"，而是表达能力不足——现有数据结构无法承载方案要求的订阅生命周期政策。

缺口 1：没有 subscriptions 表，订阅状态退化成两个字段

现状：members.plan（字符串）+ members.plan_expires_at（时间戳），辅以 orders.biz_type='plan' + plan_days。缺失：Stripe Subscription ID、Price ID、计费周期（月/年）、cancel_at_period_end、订阅状态（active / past_due / canceled / incomplete）、当前周期起止、last_synced_at。

直接后果两条政策无法表达：

  • 「到期取消，已付费周期继续有效」——plan_expires_at 只是个时间点，无法区分"用户主动取消但期末到期"和"正常到期"；
  • 「续费失败进宽限期，宽限期结束降级」——没有任何字段记录 past_due 与宽限截止时间。

5已经达标的，别重复投入

资金安全机制

  • 订单状态机原子确认（WHERE status='pending'），并发/双击只成功一次
  • order_fulfill_log 发货 outbox，UNIQUE 阶段键，杜绝"已扣款未发货"
  • points_ledger 单一事实源 + balance_after 快照，可对账
  • 回调金额二次校验（F5）

工程与安全

  • 出站 Webhook：outbox + HMAC 签名 + 指数退避 + 进程重启接管
  • 登录限速落库（5 次 / 15 分钟），跨重启生效
  • /api 写操作审计日志 + X-Request-Id
  • 付费墙 402 结构化响应（reason 区分 login/subscription/points/invite）
  • 公开页 SEO 完整：sitemap / rss / robots + 多语言端点
  • 真实 SMTP 事务邮件通道（lettre）已就绪

6建议的落地顺序

按"能否安全收到钱"排序，而不是按技术优雅度排序。整个方案不需要改架构，都是同一套 Axum + SQLite 体系内的增量。

0

止血（半天，不改架构）

删掉 update_me 的 plan 入参 → 会员 Token 回查 status → Stripe 测试模式改为拒绝 → Stripe webhook 改为"先落库、成功才返 2xx、失败返 5xx" → 验签加时间容差。做完这一步，现网的资损与丢单风险即消除。

1

订阅状态机（迁移 0010）

新增 4 张表：subscriptions / billing_operations(幂等键) / webhook_events / entitlements。付费墙判定从 plan != 'free' 改为查 entitlements；plan_expires_at 改由 subscriptions.current_period_end 驱动，明确区分 canceled（期末）/ past_due（宽限）。保留 members 上的字段做兼容回填。

2

闭环与运维

scheduler 每分钟 tick 增加：每日订阅对账、stale pending 订单自动关闭、宽限期到期降级（现在这些都是人工端点）。后台增加订阅列表、事件重放入口、对账结果视图。会员自助页增加取消续费 / 恢复续费 / 账单记录。

3

体验补齐（可选）

让 interval 真正生效（年付，tiers.price_yearly 目前是死字段）；Stripe Customer Portal 或国内等价的自助账单页；退款/争议独立状态。

7什么情况下才需要动方案里的"技术栈部分"

如果你的目标是把当前项目变成出海产品（面向海外用户直接收款），那么上面被判定"不建议对齐"的条目里，有 3 条会重新变成必要条件——但顺序仍在订阅状态机之后。

触发条件届时才需要做理由
Stripe 成为主收款渠道§6 阶段 1 的订阅状态机（前置条件）没有状态机就直接出海 = 系统性资损，不是体验问题
多币种 / 面向多市场orders 增加 currency 字段（当前只有 amount_cents，无币种）金额无币种在跨市场场景会直接算错账
海外 SEO / 多语言落地页公开页多语言 URL + hreflang（articles.locale 已有，输出缺）方案 §7 的获客要求；当前 i18n 只覆盖接口文案
收款主体与税务资格非代码问题：主体/银行账户/Stripe 可用性，或评估 Paddle 类 MoR方案说得很对——这是写支付代码之前的前置确认
客户要求企业 SSO / 多组织此时才考虑引入 OIDC IdP（先做多租户改造）Rauthy/Keycloak 的价值只在"多产品共用身份"时成立
总结：方案里"真正决定可行性的，不是技术栈里 Rust 的比例，而是登录和权限边界清楚、支付与权益能够恢复一致、数据能恢复、产品确实有销售资格"这句话是对的——而且这句话里的四项，没有一项需要换语言、换数据库或外挂 IdP。当前项目该做的是：先补掉 P0（4 条，工作量以小时计），再把订阅状态与权益从 members 的两个字段升级成独立模型（迁移 0010，4 张表）。技术栈部分保持现状即可。
