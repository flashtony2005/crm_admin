方案的方向是对的，但它把「通道」当成瓶颈，而这个项目当下的瓶颈是「供给」。

方案要做的是 Context → Intent → Capability → Action → Revenue 的映射层。而这套映射在 admin 上要成立，必须先有三个前提：有可成交的标的、有可被理解的知识实体、有可观测的信号。实测三条全部为空——tiers 0 行（无任何可售方案）、8 篇文章正文仅 55–97 字符（等于只有标题和一句摘要）、events 0 行且 visitor_id 列尚未迁移。

所以我的建议不是「照方案分十期做」，而是把十刀按依赖重排成三层：供给层（不依赖流量，现在做就有收益）→ 度量层（依赖供给产生流量）→ 通道层（必须由度量数据触发，不得提前）。其中方案里唯一「现在做就划算」的一刀是第二刀内容结构化，而第五/七刀（Capability 一等公民 + invoke API）在当前站点没有对应物——理由见第四节。

03三个前提为什么现在不成立（硬证据）

① 没有可成交的标的：tiers = 0 行

这是最刺眼的一条。方案第十节讲「Agent 帮你完成产品体验，然后把人带过来成交」，第十一节讲「Capability 分层 Free/Pro」。但实测 tiers 表一行都没有——没有任何对外可售的订阅方案。

连带效应已经在代码里显形了。render_agent_json 有三处分支专门处理「没有套餐」的情况：plans 返回空数组、subscribe 这个 action 根本不发、limits 里追加一条「当前未配置订阅方案，无付费内容与付费动作可用」。同样 articles 全部 paid_level=0，意味着 is_gated() 永远返回 false，付费墙分支、402 三态、FAQ 抑制逻辑全都在跑空路径。

所以 Agent 即使 100% 理解你、选择你、决定推荐你，它推荐过去之后也买不到任何东西。这一条不解决，方案第八/九/十节（Capability 分层、Demo 即 Proof of Value、Agent 带成交）讨论的全部场景都物理上不可能发生。

② 没有可理解的知识实体：正文 55–97 字符

8 篇文章的 content 字段长度从 55 到 97 字符，而 summary 是 14–90 字符——正文基本就是那句摘要本身。文章标题却写着「保姆级」「全网最全」「大横评」这类承诺。

这直接决定方案第二刀（Knowledge Object）的价值上限：容器已经有了（summary 是独立字段、kind 已分型、JSON-LD 由服务端派生），但里面装的东西不足以让任何 Agent 形成判断。方案第十三节说「一个真实 Intent → 一个有真实信息价值的 Knowledge Object → 多种机器/人类表达」——现在的情况是「一个真实 Intent → 一句摘要 → 多种表达同一句摘要」。

这里有个已经踩过坑的细节值得记住：FAQ 的 answer 只取 summary（上一轮定的硬规则），理由是「从正文截段会截到半句，且给正文开一条进 JSON-LD 的旁路」。这个决定在当时是对的——但它同时意味着结构化数据的质量完全绑定在 summary 这一个字段上。正文不分块，GEO 输出的天花板就是那 14–90 字。

③ 没有可观测的信号：events = 0 行，且 0015 未迁移

方案第十二节（Intent Analytics）要回答「哪些 Intent 真正产生钱」。实测：events 表 0 行、members 1 行、orders 0 行。

更需要注意的一个状态：attribution.rs 与迁移 0015_attribution 已经写好，但运行库里没有 0015——events.visitor_id 与 members.first_touch_article_id 这两列在 cms.db 里还不存在（实测报 no such column）。而且这两个文件处于未提交状态（attribution.rs、web/src/routes/content/attribution.tsx 均为 git 未跟踪，db.rs/main.rs/members.rs/perm.rs/stats.rs/tests_api.rs 已修改未提交）。看起来是并发会话的在建工作，本次评估未触碰。

结论：归因链路目前是「空跑」状态——即使现在有流量，attribution.rs 的三个查询也会因缺列直接失败。这是 L2 的第一步，而且是纯粹的收尾（代码已就绪），不是新开发。

04两处必须提出的反对意见

反对一：第五刀 / 第七刀在这里没有对应物

方案的核心创新是「Capability 成为一等公民」+「Capability API 让 Agent 替用户试一下」。这套设计成立的前提是：产品本身是一个可被调用的工具——方案自己的例子是 NCE-Flow 的 blind_listening（输入 audio_id+user_level，动作 start_blind_listening()，输出 session）。

但可可鸭是内容站：它的「能力」就是「读到一篇有用的文章」。这类站点里，read_article 已经是最强的能力了，而它归根结底是数据读取端点，不是产品能力。硬要按方案的形状造 Capability，只会得到一批 read_home/list_articles 式的伪能力——现行 /agent.json 的 capabilities 字段正是这么长出来的。

而伪能力比不声明更糟。上一轮已经定过这个原则并写进实现注释：「capabilities 只声明真实存在且实测 200 的只读端点……声明不存在的接口会让 Agent 调用失败并把整站判不可信，比不声明更糟。」把只读端点包装成「产品能力」是同一个错误的变体——Agent 会据此推断「这站有可调用的产品动作」，然后调用失败。

所以第五/七刀的正确处理是：不新造 Capability，而是把已有的 ai.rs 治理骨架（白名单 + 审批 + 审计）保留为对外开放时的现成基础设施，等站上真的出现「有输入输出契约的动作」再启用。当前该做的只有一件事：在 agent.json 里明确区分「数据端点」与「产品能力」，把 6 项从 capabilities 改名归到 data_endpoints，把 capabilities 留空——诚实地告诉 Agent「本站是内容站，没有可调用动作」，而不是让它自己猜。

反对二：第十三刀（重构核心模型）是同类风险的第二次

方案第十七节建议把原 CMS 核心模型（Page/Post/Category/Tag/Template/Theme）换成「World Model + Presentation」两层。这个抽象本身设计得不错，但本项目刚刚在这件事上付过一次学费：

  • 曾经做过 Domain Model V1：迁移 0003 建了 12 张表（sites/channels/contents/contexts/content_contexts/content_channels/templates/template_versions/site_templates/themes/theme_versions/site_themes），配 /api/v1 全契约 + 12 个 entity + 前端 4 个管理页。
  • 结果：2026-09-07 整体删除（代码侧 /api/v1 + 12 entity + 前端 4 页全删，合并到单网关 resources.rs + 单条权限链）。
  • 而表还留在库里：实测 contexts、contents、channels、sites 等至今存在且全空，无 FK、无消费方、无 UI。

这里有个讽刺性的巧合必须指出：方案第一刀要新增的 Context 对象，DB 里已经有一张空的 contexts 表了——它是上一次过度抽象的残留。谁要是把它当成「现成基础」去接，接的是一具骨架。

更重要的推论是：这个项目已经用实测证明过，先建对象模型、后找消费方，会以删除收场。方案自己的原则（不要分别维护 SEO/GEO/Agent 内容，否则又会变成三个 CMS）完全正确——但 §17 的「World Model 两层化」恰恰是同一类风险的另一个版本：在没有真实 Intent 数据的情况下先定义 Intent 的完整模型。

05补记：原文 §15 的六个技术前提，五个与实测不符

重读原文时发现一处上一版评估漏掉的关键点。原文 §15 开篇写「你现有：Axum / SQLx / PostgreSQL / Rauthy / Stripe / Askama」，并据此给出「不用推倒重来」「Auth / Billing / Entitlements 可以直接保留」的判断，以及一整套目录与 18 张表的数据库设计。但实测 server/Cargo.toml 与源码，这六项里只有一项吻合。

原文假设项目实测影响
Axumaxum 0.8（含 multipart）唯一吻合「不用推倒重来」这句成立
SQLxsea-orm 2.0（features sqlx-sqlite）。sqlx 只作为 sea-orm 的驱动，没有直接依赖数据访问形态不同：本项目的查询走 Statement::from_sql_and_values + Row::try_get，不是 sqlx 的 query! 宏与编译期校验
PostgreSQLSQLite（server/cms.db）+ Turso/libsql 双后端（turso_mode.flag 切换）；迁移是 db.rs::MIGRATIONS 内联版本化，不是 sqlx-cli方案 §15 那 18 张表是按 PG 的心智给出的。本项目单实例、迁移内联、lenient 只吞预期错误——写法与代价都不同
Rauthy（外部 IdP）无此依赖。自研 auth.rs：jsonwebtoken 9 + argon2，三级角色 + 登录限速（login_locks）「Auth 可以直接保留」成立，但保留的是自研 JWT 体系，不是 OIDC/IdP 集成。任何涉及外部身份提供商的实施细节都不适用
StripeCargo.toml 里没有 stripe crate。Stripe 是手写 HTTP（reqwest 打 api.stripe.com + 自研签名验签）。而真正的主力是微信支付 API v3：wechat_pay.rs 用 rsa 签名验签 + aes-gcm 回调解密 + qrcode 出码「Billing 已设计完整」在本项目要对到微信支付的订单/发货/兑码/退款链路上。连带发现：tiers 表带 stripe_price_id 列——两套支付渠道共用一张套餐表，配 tiers 时这条约束要先想清楚
Askama（服务端模板）无此依赖。前端是 CSR SPA（Vite + React），产物由 templates.rs 伺服；另有 async-graphql（原文未提）方案设想的「服务端渲染 + 模板层」不存在。HTML 由前端构建，服务端只做头注注入——Agent Layer 的注入机制（不改磁盘产物、改了后台配置立即生效）正是为这个架构设计的

这不是文字纠错，它带来三条执行层面的推论：

  1. 原文 §15 的目录设计本身就是一次抽象。它列了 15 个二级模块（auth/ billing/ entitlements/ context/ intent/ knowledge/ discovery/ products/ capabilities/ evidence/ actions/ agent/ content/ analytics/ jobs/），而本项目已经收敛为单网关 resources.rs + 38 个平铺模块（无二级目录）。引入 15 个目录与本项目「单网关、单权限链」的既有收敛方向相反——这与 §4 反对二是同一个问题在工程结构层的版本。
  2. §15 的 18 张新表里，contexts 与 products 已经存在。两者都是 0003 留下的空表（无 FK、无消费方、无 UI）。所以按方案动手的第一步不是「新建 contexts 表」，而是先决定这两张空表是删还是复用——否则会出现两张同名、语义不同的表。
  3. 「Auth / Billing / Entitlements 可以直接保留」这句结论是对的，但要保留的东西与方案想象的不同：是自研 JWT + 微信支付订单链，不是 Rauthy + Stripe 订阅。这不改变「不需要重写任何一块」的判断，但会影响所有涉及订阅生命周期、权益计算、支付回执的实施细节。

这条补记不改变 §06 的三层重排结论，只增加一个前置动作：任何照方案 §15 动手的人，第一步都得先把技术栈映射到实测清单上，否则会按一套并不存在的基础设施写代码。这也正是把「实测优先于文档」当成铁律的原因——原文作者并不知道这个项目的真实底座。

06重排计划：三层九步

把方案的十刀按依赖关系而非编号重排。每一层的门槛写清楚了——门槛不满足就不进入下一层，这是本计划与传统分期方案的关键区别。

L1 · 供给层

门槛：无（现在就能做，且做了立刻有收益）

只做一件事：让站上真的有「东西」——可卖的、可读的、可验证的。这一层的所有动作都不依赖流量，也不新增任何抽象模型。

S1 · 补齐可售方案（最高优先，需要你的定价决策）

  • 给 tiers 配置真实方案（先 1–2 档即可）。配置完成后会自动产生连锁效果：/agent.json 的 plans 从空数组变成真实数据、subscribe action 开始输出、limits 里那条「无付费动作可用」自动消失、FAQ 的 faq_from_facts 开始产出价格类问答。
  • 这是整条变现链路的开关。在它打开之前，付费墙代码、402 三态、订单发货、兑码核销全部处于「跑空路径」状态——测不出问题，也验证不了。

S2 · 正文补实 + 语义分块（方案第二刀的落地形态）

  • 给 articles 加一个 blocks JSON 列（不建新表、不改现有查询），按语义分块：answer（直接答案，即现有 summary）/ steps（步骤）/ evidence（实测事实）/ caveat（适用条件与不适用场景）。
  • 产出路径：后台文章编辑器改成分块录入 → 一套数据同时喂 HTML 渲染、JSON-LD、llms.txt、agent.json。这正是方案要的「一个模型，多种呈现」，但载体是现有 articles 表的一个新列，不是一套新的 Knowledge 表。
  • 为什么值得现在做：它是方案里唯一「不依赖流量、且直接提升机器可理解性」的一刀。而且它解决的正是 §3② 那个问题——GEO 输出的天花板目前被 summary 一个字段锁死。
  • 硬约束：TableDef 加列必须配集成测试。这个项目曾因 TableDef 漏列，导致 articles 的 visibility/paid_level/price_points 被网关静默丢弃、付费墙失效。新列同样会走这条路径，必须测试覆盖。

S3 · 首批 5 篇问题页（已在待办里，纯内容零工程）

  • kind='problem' 通道、/problems 总览与详情页、content_url() AC 分流全部已通，但实测 0 篇 problem。这是零代码成本、纯内容填充。
  • 素材来源已定：X 上被追问最多的问题（@KeKeYa88 的曝光是最可靠的信号源）。每页必须含至少一处只属于发布者的实测事实（开过哪张卡、被拒那次、实测损耗数字）——否则就是可复制的模板垃圾。
  • 合规口径沿用既定策略：跨境支付/加密主题只讲实测路径与损耗，不做收益承诺。首批保持 public/paid_level=0（作为流量入口）。

S4 · agent.json 诚实化与轻量补齐（方案第六刀的收敛版）

  • 改名：现有 6 项只读端点从 capabilities 移到 data_endpoints；capabilities 留空数组 + 一句说明「本站为内容站，无对外可调用动作」。理由见 §4 反对一。
  • 补 contexts：不新建表，由已发布的 tags（5 个，已是完整主题数据：name/slug/description）派生。现有 topics 已是它的弱化版，contexts 只是把它结构化（带 slug + description + 文章数）。
  • 补 intents：同样从已有数据派生——tags × kind 的组合（如「港卡」×「问题页」=「港卡怎么选」）。不发没有内容支撑的 Intent，避免声明一个点进去是空的意图。
  • 补 evidence：只放能自证的数字（已发布篇数、标签覆盖的主题数、实测事实条数）。订单数为 0 时不发——发 0 是负信号，会主动劝退 Agent。这条原则与 faq_from_facts「没套餐时不编造价格问题」一致。

L2 · 度量层

门槛：L1 的 S1+S3 完成（站上开始有可被发现的内容与可被购买的东西）

这一层的目的只有一个：用最低成本判断「Agent 到底有没有来」。注意——不是「建一套 Analytics」，而是复用已经做好的东西去回答这一个问题。

S5 · 迁移 0015 + 跑通归因（收尾，非新开发）

  • attribution.rs 已写完（含一段很扎实的设计说明：为什么用「首次触达」而非「末次触达」——末次触达会被站内推荐位、热门榜、相关阅读每一次内部跳转改写，最终几乎所有转化都归到少数流量入口，真正的获客入口被淹掉）。缺的只是把 0015 应用到运行库。
  • 前置动作：先确认这两个未跟踪文件是否是并发会话的在建工作（git status 已显示未提交）。若是，等它落地，不要并行改同一批文件。
  • 跑通后的第一个真实产出：gaps 里的 noVisitor/noRead 两列会把「链路没接上」和「接了但用户没看文章就注册」分开报——处理方式完全不同，合成一个数字就只能靠猜。

S6 · 用 404 日志当 Intent 信号的代理（方案第十二节的零流量入口）

  • not_found_log 已上线（已收 1 条），重定向表 redirects 已上线但 0 行，后台已有双标签页 + 一键转 301。
  • 改进点：把「有人（或 Agent）请求了但站内没有的路径」当成需求信号收集。这是整个系统里唯一不需要用户行为数据就能获得 Intent 信号的入口——而它已经建好了，只是目前只被当作 SEO 卫生问题看待。
  • 具体做法：后台给 not_found_log 加一个「按路径聚类」视图，标出「高频未命中路径」。这些路径直接就是下一批问题页的选题清单。

S7 · 让 AI 渠道可测（复用 Smart Links，不建 Discovery Layer）

  • /go/{token} + link_clicks 已经在跑（区分真点击与预取，UA 黑名单刻意不含 headless 因为自家 e2e 就跑在 headless Chromium 上）。
  • 改进点：给 llms.txt / agent.json 里输出的 URL 挂上带 token 的短链。这样就能回答方案的第三刀真正要问的问题——「Agent 是否真的来读了、读了多少次」。
  • 为什么不用自建 Discovery Layer：方案第三刀建议的 discovery/（context/intent/knowledge/candidates/ranking/recommendation）是一个搜索引擎的架构。要验证「Agent 有没有发现我」，一条带 token 的 URL 就能回答；自建索引层要回答同一个问题，成本高出两三个数量级，而且它解决的问题（在候选池里排序）只在「有人来搜」时才存在。

L3 · 通道层

门槛：L2 观测到非零的 Agent 来源访问（不是预测、不是推测，是日志里的真实记录）

这一层才是方案的主体（Context/Intent 一等对象、Knowledge Graph、Capability API、Discovery 主动登记）。我的建议是：现在连设计都先不做，但把触发条件写死在 L2 的验收标准里。

  • 触发条件 A（对应 Context/Intent 一等对象）：L2 的 404 聚类里出现同一意图的多个不同问法，且这些问法没有对应页面。这证明「Intent 是独立于页面的实体」——这个证据成立，才值得为它建表。
  • 触发条件 B（对应 Capability API）：站上出现真的有 invoke 语义的东西（有输入、有输出、有副作用）。可可鸭当前没有，所以不触发。若将来接入 NCE-Flow 那类工具型产品，ai.rs 的白名单+审批+审计骨架可直接复用为对外能力网关。
  • 触发条件 C（对应 Knowledge Graph / Discovery Layer）：≥1 个真实产品（不是内容）且 ≥10 篇有实质内容的知识对象。products 表当前 0 行。

这一层的设计原则已经由 L1 的 S4 铺垫好了：agent.json 里的 contexts/intents/evidence 三段在 L1 就用派生方式给出（从 tags/articles 推），而不是新建表。这样 L3 真正要建表时，已经有真实的消费方在等着——而不是先建表再找谁用。这正是 0003 域模型那次教训的反向操作。

07明确不做清单

有观点地列清楚哪些不做，比列要做什么更能防止走偏。以下五条我建议明确否决，理由都来自本项目自己的实测教训。

不建议做理由
另做一套独立 GEO 系统方案自己也说了这一点（「不要分别维护 SEO 内容、GEO 内容、Agent 内容，否则最后又会变成三个 CMS」）。这不是理论担忧——0003 域模型的 12 张空表就在库里躺着。
把只读端点包装成 Capability会导致 Agent 推断「本站有可调用动作」然后调用失败，比不声明更糟。现行 capabilities 的 6 项应改归 data_endpoints，capabilities 留空并说明缘由。
自建 Discovery Layer（索引/排序/推荐）要回答的问题是「Agent 有没有发现我」，一条带 token 的 URL（现成的 /go/{token}）就能答。排序问题只在「有人来搜」时才存在，当前 0 流量，排序对象为空。
按方案 §17 重构核心模型为两层本项目刚删过一套同类抽象（/api/v1 + 12 entity + 前端 4 页），且留下了 12 张空表作反例。先建对象模型、后找消费方，在这个项目上已被实测证明会以删除收场。
用 AI 批量生成 SEO 页面方案第十二节自己设了原则「不是批量生成垃圾 SEO 页面」。而实测现状（正文 55–97 字符）恰恰意味着：自动生成的上游原料本身是空的，生成出来只会是同一句摘要的 N 个变体。自动生成层（第十一刀）的前提是 S2 完成，不是相反。

08需要你拍板的三个决策点

决策 1 · tiers 什么时候配、配什么？阻塞整条变现链路

这是唯一一个必须由你决定、且技术侧无法代劳的点：定价与方案划分。它阻塞的东西比看起来多——plans 空数组、subscribe action 不发、付费墙走空路径、订单全链路无法验证。哪怕先配 1 档占位方案，也能让整条链路从「不可测」变成「可测」。

决策 2 · blocks 语义分块现在就做，还是先纯补正文？

两条路各有代价：先做分块后写内容，可以一次录入到位，但后台编辑器要改（后端加列 + TableDef + 集成测试 + 前端编辑器，约 1 个批次）；先补正文（用现有 content 字段直接写长）见效最快，但将来分块时 8 篇内容要返工重录。

我的倾向是先做分块——因为返工的内容是「只属于发布者的实测事实」，那是你最稀缺的原料，不应该录两遍。

决策 3 · attribution.rs / 0015 那批未提交改动，是并发会话在做吗？

实测显示 attribution.rs、web/src/routes/content/attribution.tsx 为 git 未跟踪，db.rs/main.rs/members.rs/perm.rs/stats.rs/tests_api.rs 已修改未提交，而运行库缺少 0015 的列。这符合「另一个会话正在做归因层、尚未收尾」的特征。

按项目既有约定（重链接前必 taskkill、勿反复拉起、避免互相 os error 5），本次评估未触碰这些文件、也未编译后端。如果那是你在别处推进的工作，S5 应等它落地；如果不是，我可以接手收尾。

09一句话总结

方案把 CMS 从「管内容」升级到「管理意图到行动的映射」，方向是对的；但在这台机器上，当前缺少的不是映射层，而是被映射的东西。

已经建成的部分比方案假设的多得多——Agent Manifest、llms.txt、AI 爬虫声明、服务端头注、JSON-LD、付费墙机器口径、Smart Links、归因链路，这些几乎覆盖了方案第三、六、九刀的形态。真正缺的是三样：一个可售方案（tiers=0）、一批有实质内容的文章（正文 55–97 字符）、一条能记录访问的链路（events=0 且 0015 未迁移）。

所以正确的动作顺序是 L1 供给（S1–S4）→ L2 度量（S5–S7）→ L3 通道（门槛触发），而不是照方案编号从第一刀往下推。Context/Intent 一等对象该做，但要在 404 日志里真的出现「同一意图的多种问法」之后再建表——那时建出来的表有真实消费方等着，而不是像 0003 留下的那 12 张空表。

动手前的最后一个提醒（见 §05）：原文 §15 假设的六项技术前提里，只有 Axum 一项与实测吻合，SQLx / PostgreSQL / Rauthy / Stripe / Askama 五项都不对——实际是 sea-orm + SQLite/Turso + 自研 JWT + 微信支付 + CSR SPA。照着 §15 的目录与表设计直接开工，等于按一套不存在的基础设施写代码；而且那 15 个二级目录本身就是一次结构抽象，与本项目「单网关 + 单权限链」的收敛方向相反。
