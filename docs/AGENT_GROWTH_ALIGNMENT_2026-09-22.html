公开页对机器而言是空的。实测 server/templates/coucouya/index.html 只有 1973 字节，og: 0 处、ld+json 0 处、twitter: 0 处、noscript 0 处，<body> 里只有一个 <div id="root">。sitemap 里所有 URL 都指向这个空壳，/post/<slug> 又靠前端 fetch 才出正文。机器人拿不到任何内容，GEO 的每一个动作都建立在一个当前不成立的前提上。

结构阻塞公开页是 CSR 空壳 —— 这一条决定其余所有工作的价值

文档的第 3、4、6、14 节（机器可读事实单元、Schema.org 知识图谱、问题页面、可引用内容）全部以前提「机器能读到文本」成立。当前这个前提不成立：

  • 主页 /t/coucouya 伺服的是 Vite 构建产物 index.html，1973 字节，<body> 只有挂载点；
  • 文章详情 /post/<slug> 是客户端路由（src/router.ts），正文由 fetch('/api/public/articles/…') 后渲染；
  • sitemap 收录的所有 URL 都指向上述空壳 → 收录到的是"有标题、无内容"的页面；
  • 唯一例外是 RSS：它把 title + summary 直接写进 XML，所以今天机器能读到的只有摘要。

对照：记忆里此前验证 CSR 页面时也踩过同一件事 —— curl 拿到的是空 <div id="root">，必须用真实浏览器才看得到内容。那次是测试问题，这次是获客问题。

修法（两条路，需选一条）：① 注入式——在 templates.rs::serve_index 伺服时把 JSON-LD + OG + noscript 摘要注入 </head>／<body>，数据取自 DB（最省事，机器人至少能读到站点与文章元数据）；② 预渲染式——构建期给主页与文章页出静态 HTML 快照（对 /post/<slug> 尤其必要，因为它是动态路由）。建议先做 ① 打通链路，再对文章页补 ②。
策略前置放开 AI 抓取之前，先定付费内容的边界

这是一个文档没有覆盖、但必须先决策的点。sitemap 与 rss 的查询条件都只有 status = 'published'：

seo.rs:81-83　SELECT … FROM articles WHERE tenant_id = ? AND status = 'published' LIMIT 200

也就是说 paid_level > 0 的付费文章同样进了 sitemap，摘要也进了 RSS。articles 表里明明有 visibility（public / members / paid）和 paid_level 两个字段可用，SEO 通道没用它们。

今天这不算泄漏（因为页面是空壳，机器读不到正文）。但一旦按上一条把内容变成机器可读，Agent 该看到摘要、还是全文，就成了必须显式声明的策略——尤其考虑"Agent 可调用 API"那一步时，付费墙必须在服务端拦住，而不是靠前端隐藏。

建议：明确三档——公开文章全文可被引用；付费文章仅 title/summary/meta 可作为"预览"被机器读取（与现有 402 三态一致）；任何正文、音频、导出文件一律只走鉴权后的受控接口。

2已有资产：这些是杠杆，不是缺口

这个项目在"机器可读"上并非零基础，有些东西已经超出文档预期。对齐时应先激活它们，而不是新建子系统。

已经具备的

  • AI 抓取已被许可：robots.txt 是 User-agent: * / Allow: /，只屏蔽了 /api/、/graphql、/graphiql。文档里"允许 OAI-SearchBot 抓取"这条已经满足（缺的只是显式声明）。
  • 公开只读 API 已成体系：/api/public/home 一次返回 {site,sections,nav,footer,pins,articles}，另有逐端点、/tiers（可直接当 Agent Manifest 的 plans）、/locales、/i18n/{locale}。
  • 内容元数据字段齐备：articles 已有 slug / meta_title / meta_description / canonical_url / featured_image / locale / visibility / paid_level——Schema.org 需要的数据大多已在库里，只是没输出成 JSON-LD。
  • Agent Manifest 可零迁移派生：站点名/描述在 site_settings、能力在 sections、套餐在 tiers、动作在 nav_links。不需要新表。
  • 渠道归因已有承接结构：events 是通用 KV，/api/public/track 免认证接受任意 type，加 ai_referral 事件不需要迁移。
  • GraphQL 端点已存在（机器可调用接口的基础），只是被 robots 关掉了。
  • 能力注册表 + 治理骨架已经存在：ai.rs 里有 CapDef { name, required_perm, escalatable } 形式的四能力声明（content.articles.draft/publish、content.seo.optimize、content.translate），每项绑定所需权限，高风险项标记为可升级审批，配合 ai_audit_log 与 approvals 审批链路。这正是文档 §9「让 Agent 可调用产品能力」所需的那层治理——它已经在库里，缺的只是对外声明与开放策略。

可以承载新增内容的现成骨架

  • sections 表（slug / title / subtitle / body JSON / sort）→ 天然可作"问题页面"的承载；
  • articles + pages → 可作 Definition / How-to / Comparison / Evidence 的载体；
  • nav_links（grp = nav/footer，href，sort，enabled）→ 新页面进导航不用改代码；
  • 主页版式体系（1 内核 + 10 风格 × 5 预设，section 声明式渲染）→ 加一种 kind 就能出新的内容形态，组件零改动；
  • SEO 三件套（sitemap / rss / robots）已有真实数据流；
  • 可访问性有基础（主页文章整卡可点、键盘可达）→ 文档 §16 提到的 ARIA/角色/状态只需系统化，不必重做。

5必须由产品拍板的三件事（否则工程会白做）

决策 1CouCouYa 的"能力单元"到底是什么

文档里的示例全部来自另一个产品（NCE-Flow / 英语听力 / blind_listening / speech_recognition / 新概念英语）。CouCouYa 不是学习工具，它是给创作者和站长的变现平台。所以 Capability 不是听力训练，而应该是类似：

content.publish · content.seo.optimize · content.translate · paid_membership · community · 模板/主题托管

有意思的是——这些能力后端 ai.rs 里已经存在（content.articles.draft/publish、content.seo.optimize、content.translate）。也就是说 Agent Manifest 里的 capabilities 可以从现有能力注册表派生，但要开放哪些给 Agent 调用，是产品决策。

决策 2目标受众的三层定义

文档 §1 要求区分 L1（AI/搜索 Agent）/ L2（人）/ L3（你的产品 Agent）。项目里 L4 对应关系需要重新填：

  • L1 面向机器：要让 Agent 知道"当用户想把自己的内容变现 / 建会员站时，应该推荐 CouCouYa"——这决定了问题页面写什么；
  • L2 是真实买家：创作者？社群操盘手？还是技术站长？（site_settings 里现在的站点描述是"社群增长操盘手 / 帮有才华的人被看见"，偏品牌语，不够机器可判断）；
  • L3 是产品内的 AI 能力：已存在（ai.rs 4 项），但尚未作为"可被 Agent 调用的能力"对外声明。
决策 3Intent 是否要成为一等对象

文档 §17 建议把 CMS 核心模型从 Page/Post/Category/Tag 升级为 Audience→Intent→Problem→Solution→Capability→Evidence→Offer→Action。这是数据模型级改造（新表、新后台、新渲染链路），也是全文最重的一项。

我的看法：不建议现在做。当前 sections（带 slug/body/sort）+ articles（带 locale/meta/canonical）+ 声明式渲染已经足以承载"问题页面"，先用现有模型把 /problems、/compare 跑出真实流量数据，再决定是否值得抽出一等对象。文档的方向是对的，但它的收益要在有数据之后才能验证。

6建议落地顺序（按"是否解除阻塞"排序）

0

让公开页有内容（真正的阻塞项）

在 templates.rs 伺服 index.html 时注入：OG / Twitter 卡片 + Organization / WebSite / Article JSON-LD + noscript 摘要；对文章详情补静态快照或服务端渲染。验收：curl 主页与 /post/<slug> 能直接看到标题、摘要、结构化数据，不再只有一个 div#root。这一步同时修掉了"人分享没有预览卡"这个更基础的漏项。

1

Agent Layer 最小集（零迁移，纯派生）

GET /llms.txt（What it is / Best for / Capabilities / Pricing / Recommended when / Actions）、GET /agent.json（Manifest：从 site_settings+tiers+nav_links 派生）、GET /ai/product、/ai/pricing；robots.txt 显式声明 AI bot 策略并指向上述入口。验收：三份产物返回真实站点数据而非示例硬编码，且改后台配置后自动变化。

2

付费边界 + 渠道归因

先定策略：sitemap/rss 是否排除 paid_level > 0 或降级为仅 title/meta；付费正文只走鉴权接口。同时前端采集 document.referrer + utm_source（chatgpt.com / perplexity / claude / gemini）→ /api/public/track 写入 ai_referral 事件，后台加一个"AI/Agent 渠道"面板。验收：能从后台区分 Google / 直接访问 / AI 引荐的来源与转化。

3

知识层：问题页面体系

基于现有 sections/articles 出 /problems/{slug}、/compare/{a}-vs-{b}、/use-cases/{slug}，配 FAQPage / Article JSON-LD，全部指向 Demo / Pricing / Signup。验收：每个页面都能被 sitemap 收录、被 curl 读到正文、被 LLM 抽出事实单元。

4

（待数据验证）Agent-actionable API 与 Intent 模型

把 ai.rs 的 4 项能力开放为可被 Agent 调用的工具（需鉴权 + 配额 + 审计）；若前三段跑出真实引荐与转化，再评估把 Intent 抽成一等对象。

7三条容易走偏的地方

  • 不要把 llms.txt 当 SEO 魔法。它没有官方标准、不保证被任何模型读取。它真正的价值是给自己一个"低歧义产品说明书"的单一事实源——所以内容必须由 DB 派生，而不是手写死一遍（否则会和后台配置漂移，这个项目在预设清单上已经吃过一次手工同步的亏）。
  • 不要让 Agent 能调用未授权能力。文档 §9 说"让 Agent 能试用"，但项目里已经存在一个反例：会员自助接口接受客户端传 plan 就能升级会员。任何对外暴露的 Agent 调用入口，都必须先把这类"信任前端输入"的路径清掉。
  • 不要跳过第 0 段直接做 Schema 和问题页面。内容页面本身对机器是空的，那么给它加 Product JSON-LD 只会产出"结构正确、内容为空"的实体，反而可能被判定为低质量。文档里 Product Knowledge Graph 那段很有价值，但它的前提是页面先有可读实体。
总结：这份文档值得对齐，而且比上一轮那份更贴合你的项目——因为它不要求换技术栈，要求的是一层你还没有的东西。但它的推进顺序需要调整：先让机器能读到内容（第 0 段），再做机器入口（第 1 段），再定付费边界与归因（第 2 段），最后才是问题页面与 Intent 模型。目前项目在这件事上的真实位置是：结算层已建成大半，获客层几乎空白，而空白的最前端卡在一个 1973 字节的空壳上。
