1P0-1 重定向管理器 + 404 监控

对标 Rank Math 免费版做的那件事。之所以把它排第一：我们正在主动制造 URL 变动 —— 迁移 0011 加了 kind 列， 文章可以在 /post/<key> 与 /problems/<key> 之间迁移；sitemap 刚扩过。 没有 301，旧地址就是 404，而这类流失既不报警也查不到。

出：访问 /post/old-slug → templates::serve_file 在 SPA 兜底之前 查重定向
    → 命中 → 301/302/307/308/410（累加 hits）
入：前端渲染出「未找到」兜底态 → POST /api/public/not-found → not_found_log 按路径 upsert

两个必须记住的架构事实

  • 重定向只能放服务端：爬虫不执行 JS。放在前端路由层，对搜索引擎与 AI 爬虫等于不存在。
  • CSR 站点服务端收不到 404：服务端对任意导航路径都回 index.html， 所以 404 只能由前端主动上报。这是 CSR 架构的固有代价，不是实现选择。

路径口径

统一存完整请求路径（含 /t/<slug> 前缀），匹配时先试完整路径、未命中再试剥掉前缀的站点相对路径。 这样后台「一键转 301」可以直接把 404 日志里的 path 落成 from_path，零转换且与匹配逻辑天然一致。

2P0-2 评论区升级为社区最小闭环

原状态：公开站连评论组件都没有。评论区只有「读者对作者」，没有「读者对读者」，因此不产生任何留存。 这是会员站 —— 会员留存即收入留存。

能力实现要点
反应（点赞/有用）切换语义（点两下回到原状），不是只加不减；匿名一律 401 —— 匿名可刷的计数不是信号，是噪声
楼中楼复用 0004 已建的 parent_id；回复落库时给对方发通知，否则楼中楼只有发起方知道，不成对话
@提及只按昵称精确相等匹配本站会员并去重：模糊匹配会把消息发给无关人，通知错人比没通知更坏
举报同一人重复举报不新增（靠唯一索引，不靠应用层先查后写）；达阈值 3 自动转 pending 进审核队列
审核队列补上权限（此前只要登录就能改审核状态）+ 按举报数降序排（按时间排会让被举报的沉到第 200 条之后）
会员身份OptionalMember 提取器永不拒绝：过期令牌当匿名而非报错，不该让访客连评论都读不了
明确不做：私信、活动流。社区体量不够时，空的活动流比没有更伤 —— 它向每个新访客证明"这里没人"。 这条判断同样重要：抄功能形态容易，抄得住"什么时候不该做"才难。

3P0-3 会员 360° 档案时间线

零新表 —— 数据早就在库里，只是没人把它们聚到一个人身上。聚合 orders / points_ledger / comments / events（带 type LIKE 'member.%' 白名单）+ members.created_at， 后台会员列表加「动态」入口。

刻意排除：form_submissions。它没有 member_id 列 —— 硬按邮箱去猜归属，会把别人的表单记录挂到这个会员头上。宁缺，不错归属。

4P0-4 Smart Links

私有化站点没有 Google Analytics，也没有第三方像素。「我发出去的那条链接到底有没有人点、点的都是谁」， 只能靠自己伺服一个 /go/{token} 来回答。它是本站唯一能拿到的用户行为信号。

挂在服务端根路径而非任何前缀下：短链要能贴进邮件、微信群、短信 —— 那些地方没有 /t/<slug> 这种 base 概念。

三条非显然的设计决定

决定不这么做会怎样
302 必须带 Cache-Control: no-store 302 本身可缓存。一旦被中间层缓存，后续点击根本不到服务端 —— 跳转照旧成功、计数静默停在第一个人的数字上。最难发现的一类坏。
预取照旧跳转、只是不计数 邮件网关和 IM 会先抓一遍链接做预览。跳错比不跳伤害大，所以观测可以缺、功能不能缺。 计数拆成 clicks / prefetch 两列：混在一起， 一封发给 200 人的邮件在无人点开时就能显示"200 次点击"。
判真人靠 Sec-Fetch-Mode: navigate，UA 黑名单不含 headless UA 黑名单只兜老式网关。刻意不把 headless 列进去 —— 我们自己的端到端验证就跑在 headless Chromium 上，列进去会让真实点击在自测里也统计不到。 验证手段把被测行为屏蔽掉，是最容易蒙混过关的一种错。

点击者会被自动打上链接上配置的标签（member_tags，幂等靠唯一索引），并在 P0-3 的档案时间线里露出 —— 两个功能在这里接上了：标签不给任何人看，就等于没打过。

5本轮发现并修掉的既有缺陷

这四条都不是"新功能没写完"，而是既有代码里的洞 —— 写新代码时才会踩到。

#缺陷为什么之前没被发现
1 redirects.tsx 一直有 tsc 错误 上一轮（P0-1）根本没跑 tsc。根因：CrudService.create 的入参是「完整实体」， hits/enabled 这类服务端字段也必须显式给初值。写 P0-4 页面时同类错误一起暴露。
2 评论集成用例的 setup 与断言方向相反 用例写「甲发评论 @阿乙」却断言「被 @ 的甲收到通知」。 实际通知正确地发给了乙 → 用例失败。但如果当初实现也恰好写反了，用例会通过，缺陷被永久掩盖。 已拆成「甲发无 @ 评论 + 乙发评论 @阿甲」，方向唯一。
3 parse_mentions 停用符漏了 . 点号在昵称里罕见、在域名里必现。a@b.com 会解析出 b.com 去查会员表。
4 后台资源列表把 url 渲染成 <a href> 后端已拒绝把 javascript: 用作跳转目标，但后台列表自己的 <a href> 点一下仍会在后台执行 —— 跳转防护救不了这个面。已改为非 http(s) 只显示文本并标「非法」。
第 2 条值得单独记：写涉及「方向」的断言时（谁通知谁、标签打给谁、计数算在谁头上）， setup 与断言必须指向同一个人，并在注释里写清方向。 方向写反的测试不只是没覆盖到 —— 它会给缺陷盖章，比没有测试更危险。
