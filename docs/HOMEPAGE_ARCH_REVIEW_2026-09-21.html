1 主页没有生产形态
manifest.json · DEPLOYMENT.md		 coucouya 是 kind=app + 硬编码端口 5199，属于「外部已注册应用」，后端不伺服它——spa_fallback 只提供 web/dist（运营后台，main.rs:83-108）。而 coucouya/ 下连 dist/ 都没有，部署文档里也只字未提 5199。结果：主页的唯一运行方式是开发服务器 npm run dev，没有产物、没有托管、没有守护、没有开机自启。 二选一：
A（推荐）把主页也变成「可托管产物」——构建后落到 server/templates/coucouya/，由 /t/active 同源伺服，一个进程解决；

2 回环地址硬编码
coucouya/index.html 内联脚本
coucouya/src/api.ts:118		 主页头部有一行内联 JS 直接 fetch('http://127.0.0.1:8088/api/public/templates') 来决定是否跳转到激活模板；api.ts 里 CMS_ORIGIN 默认值同样是 http://127.0.0.1:8088。生产域名下这是**跨域请求且指向服务器本机回环**，必然失败；而失败被 catch 静默吞掉 → 模板切换能力"看起来在、其实不在"。叠加 CMS_ENV=production 且未配 CORS_ORIGINS 时跨域被拒（main.rs:244-247），问题更隐蔽。 改同源相对路径 /api/public/templates（生产由同域反代承载）；确需跨源则统一走 VITE_CMS_ORIGIN，并在构建期注入、缺失即报错。
3 上传模板与 API 同源
templates.rs::serve_file
main.rs:229-232		 /t/{slug} 由 8088 本体伺服，也就是**模板包里的任意 JS 运行在 API 的源上**。而模板是后台上传的 zip（20MB、任意 HTML/JS）。同一源意味着它可以直读 localStorage 里的后台 token、直接调管理接口。全仓检索 CSP / X-Frame-Options / nosniff 零命中，没有任何兜底。 把模板托管挪到独立 origin（子域或另一端口）；退一步至少在模板响应上加严格 Content-Security-Policy，并让预览走 sandbox iframe。上传模板只对 Owner 开放。

  • 内容与形态解耦。换模板不需要动内容，改内容不需要动模板；sections 用独立表而非塞进 KV，新增区块无需改表结构。
  • 激活即指针。activate() 只切一个指针，不做数据搬迁，这个抽象是对的（问题只在指针存了两份）。
  • 模板托管的安全边界修过。slug_ok 白名单 + extract_zip 目录穿越防护 + manifest 拒绝直读，F5 那轮补得很到位。

新发现（2026-09-22）：coucouya 不在版本控制下

主页的代码库 F:\project\coucouya 不是 git 仓库（git rev-parse 报 not a git repository，也无 remote）。而它现在已经不只是模板——它是产品对外的主入口， 内含 base 感知路由、白名单 HTML 净化器、付费墙 UI、4 档主题、部署脚本等自研代码。

风险：没有历史、没有 diff、没有回滚、没有异地备份。scripts/deploy_to_admin.py 把构建产物同步进了 admin 仓库的 server/templates/coucouya/，那只是压缩后的 bundle——源码一旦误删或改坏，无法从产物还原。

建议：尽快 git init + 建 remote 并首次提交；node_modules/、 dist/ 保持忽略。不要只依赖 admin 仓库里的构建产物版本。

另：server/templates/coucouya/（约 380 KB 构建产物）目前在 admin 仓库里是未跟踪状态， 需要决定是「入库（clone 即可跑，但需与源码同步）」还是「忽略（保持仓库干净，靠 scripts/deploy_to_admin.cmd 生成）」。建议后者 + 在 README 写明部署步骤。
