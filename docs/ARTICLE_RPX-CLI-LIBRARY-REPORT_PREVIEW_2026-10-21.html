rpx library 与 report：目录库里的报表生命周期

从「一份文件」到「一个库」

前面几篇讲的都是单份模板的操作：lint、run、patch。但真到工程里，你面对的是几十份报表、多个版本、谁改过什么、上次跑的结果是什么。

rpx library 和 rpx report 就是为这个尺度准备的（前四篇分别讲自描述、静态检查、执行导出、模板补丁）：目录库（library）是报表定义的家，report 是库内报表的完整生命周期。

library init：建一个库

rpx library init my-reports

注意 <DIR> 是位置参数，不是 --dir。建完之后目录里是两个文件：一个 .library.json（库清单）和一个 .gitignore——库被设计成可以直接进 git 的，这就是「定义即代码」落到工程上的样子。

想直接要一批可跑的样例，加 --presets：

rpx library init my-reports --presets

实测它会把 5 份预制报表（区域分组销售、复杂主格经营分析、多栏报表、统计图集、图片与背景）连模板带数据一起放进库里，每份一个目录：

my-reports/
  .library.json
  .gitignore
  grouped-sales/
    manifest.json
    template.json
    data/sales.csv
  ...

每份报表由 manifest.json 描述：id、name、description、tags、template、data_dir、version。数据跟着定义走（data/ 目录），所以一份报表是自包含的，拷给别人就能跑。

report：12 个动作

库内报表的生命周期命令有 12 条，按用途分：

动作用途
list列出库内报表（带结果状态与修订号）
show看某份的源码与状态
validate离线校验（同 template validate）
run运行库内报表
runs查看运行历史
copy / delete复制 / 删除
patch应用 RFC 6902 补丁
update改名称 / 描述
import-json从外部 JSON 定义入库
migratev0 → v1 模板迁移（可备份）
prune清理旧运行记录

revision：库内写入的乐观锁

这是目录库设计里我最想讲的一点。

每次 report list 或 show，每份报表都会带一个 revision 字段——实测是一个 sha256（如 d90469fb…40ee73）。任何库内写操作都必须带上它。

rpx report show --library my-reports grouped-sales   # 取 revision
rpx report update --library my-reports grouped-sales \
    --name "区域销售（2026）" --if-match d90469fb...

不带会怎样？

不是「警告一下继续」，而是命令根本跑不起来：--if-match 在参数层就是必填项，缺了直接返回 USAGE（退出码 2），并提示缺少哪个参数。

带错了会怎样？

我用一个错误的修订号实测：

rpx report update --library my-reports grouped-sales \
    --name "新名字" --if-match deadbeef
REVISION_CONFLICT | 源码已变化，请重新读取后处理修改

错误信息很明确：你手里的修订号过期了，重新读一次再改。

为什么值得单独设计？

因为报表定义是多人、多进程、还会被 Agent 改的东西。典型事故是：A 读了一份定义，慢慢改；这期间 B 已经改过一版；A 再写回去，把 B 的改动整个盖掉——而且不会有任何报错。

revision 把这种覆盖变成了一个明确的失败：REVISION_CONFLICT，并告诉你该怎么办（重新读取）。这对 Agent 尤其重要——它最容易在「读—想—写」的长间隔里拿到过期上下文。

顺带一个实测发现：REVISION_CONFLICT 是真实会返回的错误码，但它不在 rpx capabilities 的 32 条错误码清单里（清单里只有 REVISION_REQUIRED）。所以别只依赖错误码清单做兜底判断，把错误信息本身也读进去。

run 与 runs：运行留痕

库内运行同样要带 revision：

rpx report run --library my-reports grouped-sales \
    --if-match d90469fb... --export csv

产物不是写到随便一个目录，而是进库内的运行记录区：

my-reports/.runs/grouped-sales/run-01792541419425929300-8712-0/artifacts/...

实测返回里同时给了 layout（含 page_count）、result、workbook 三个路径。也就是说每一次运行都被留在库里了，不是跑完就散。

然后可以随时回看：

rpx report runs --library my-reports grouped-sales

返回分页的运行记录（items / total / next_offset）。跑久了记得用 report prune 清理旧记录，否则 .runs 会一直长大。

这套「运行留痕」配合 result.json 里的 origin 字段，就形成了一个可追溯的链条：这次结果 → 哪次运行 → 哪份定义（revision）→ 哪个数据（sha256）。这篇讲过 run 产物里的溯源字段。

什么时候该用库，什么时候不用

不是所有场景都需要库。我的判断标准：

  • 用单文件 + CLI：一次性导出、脚本里临时跑、CI 里校验。轻量，不需要状态。
  • 用目录库：报表数量上到两位数、多人协作、需要留运行历史、需要版本化。

库的代价是多一层结构和 revision 约束；收益是可追溯、可协作、可回滚——而且因为它就是一堆 JSON 加一个清单文件，整个库可以直接 git 管理，评审和回滚都用你已有的工具。

常见问题

--library 每次都要写吗？

是的，库路径没有全局配置项，每个 report 子命令都要显式给。好处是一台机器上可以同时有多个库互不干扰（比如按客户、按环境分）。

能直接改库里的 template.json 吗？

能——它就是一个文件。但要清楚后果：直接改会让 revision 变，而你手里的旧 revision 就过期了，下次用旧值写入会拿到 REVISION_CONFLICT。改完重新 report show 取一次就行。要走正规流程就用 report patch。

migrate 是干什么的？

把库内的 v0 模板迁移到 v1（当前定义格式是 rpx-report/v1）。支持备份，所以迁移前会留一份原文件。老库升级时用它。

delete 也要 revision 吗？

要，而且删除是库内最危险的操作，设计上强制要求先读到最新状态再删。这跟「必须带修订」是同一条规则——所有写操作（含删除）都必须基于你刚刚确认过的状态。

库能搬到别的机器吗？

能。.runs 里的历史记录如果不需要，可以先 prune 掉；剩下的全是 JSON、CSV 和清单，整个目录拷走或提交到 git 都可以。
