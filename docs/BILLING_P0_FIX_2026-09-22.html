2四条 P0 逐条：根因 / 修法 / 实测证据

P0-1 资损会员可自助升级 —— 客户端 plan 直写库已修

根因：members.rs::update_me 的 MemberUpdate{ name, plan } 把请求体里的 plan 当普通字段直接写进 members.plan；而付费墙 subscribed() 只认「plan != 'free' 且未到期」，且 plan_expires_at 为空被当作「不限期」、解析失败也被当作「不限期」。两个宽松叠加 = 注册（member_invite_required=off 时默认开放）拿到会员身份后，一次 PATCH 即永久解锁全部 paid_level=1 内容。

修法（两处，一堵一收）：

① 写入口收口 — update_me 里只要 req.plan.is_some() 立即 return Err(ApiError::bad("会员套餐不可自助修改，请通过购买订单或兑换码升级"))。plan 的唯一合法写入口 = 订单发货 / 兑码核销 / 后台管理。
② 判定改安全默认 — public_api.rs::MemberGate::subscribed() 把 plan_expires_at 解析失败由 Err(_) => true（视为不限期）改为 Err(_) => false（视为无权），并加 active() 前置。

实测证据（隔离探针实例，非主库）：

P0-2 资损Stripe 未配置 / 测试模式静默发会员已修

根因：subscriptions.rs::checkout 里 STRIPE_SECRET_KEY 缺失、或 tier 没有 stripe_price_id 时，代码走「演示分支」直接把 members.plan 置为 tier_slug + status=1，并返回一个 ?demo=1 成功页。即：只要 Stripe 没配好，任何人都能自助白拿会员。这个分支在生产环境同样生效。

修法：抽出纯函数 decide_checkout(sk, price_id, demo_flag, is_prod) -> CheckoutMode，三态明确：

判定顺序条件结果行为
1（最优先）密钥 + price_id 均就绪Live走真实 Stripe Checkout，并带 subscription_data[metadata][member_id] 便于后续订阅事件定位会员
2未就绪 且 STRIPE_DEMO_MODE=1 且 非 productionDemo仅演示放行，eprintln! 告警；production 下该分支被禁
3其余所有情况Denied返 400 + 可操作原因（缺密钥 / 缺 price_id / 生产禁演示）
顺序有讲究：先判 Live 而不是先判 Demo。否则生产上一个历史遗留的 STRIPE_DEMO_MODE=1 就能免费发会员。已写进断言 decide_checkout("sk_test","price_1",true,true) == Live。

P0-3 丢单Stripe Webhook 失败仍返 2xx · 无幂等 · 无落库已修

根因：subscriptions.rs::stripe_webhook 旧实现三个问题叠加 —— ①事件不落库；②没有 event_id 去重；③DB 更新用 .ok() 吞掉错误后仍然返回 {"received":true}（2xx）。Stripe 见 2xx 即认为投递成功，不再重试 → 事件永久丢失、订单永不发货。另外只处理 checkout.session.completed，续费/失败/取消/退款全部无响应；验签无时间戳容差（可被重放）。

修法（迁移 + 重写处理流程）：

① 迁移 0010_webhook_events — 新表 webhook_events(id PK, tenant_id, provider, event_id, type, payload, status, attempts, last_error, applies_at, created_at, updated_at)，含 idx_webhook_event_unique UNIQUE(tenant_id, provider, event_id) 与 idx_webhook_event_status。纯追加，不改既有表。
② 先入库后处理 — 进函数第一件事是 INSERT 事件做幂等占位；插入冲突即视为「已处理过」，直接返 2xx（带 duplicate:true）；插入成功才继续 apply，成功标 processed / pending_apply / ignored，失败标 failed 并返 5xx（ApiError::server），让 Stripe 按它自己的节奏重试。
③ 补事件类型 + 验签容差 — customer.subscription.* / invoice.* 归为 Applied::PendingApply（落库待阶段 1 状态机消费，不再静默丢弃）；verify_stripe_sig 加 now 参数与 STRIPE_SIG_TOLERANCE_SECS = 300 时间容差。

P0-4 越权会员 Token 不可撤销 —— 只验签不回查 status已修

根因：members.rs::MemberAuth 提取器只做 JWT 验签，不回查 members.status；会员 token 有效期 30 天、tv 固定为 0 不参与版本比对。管理员侧早已修过（auth.rs 逐请求回查 status + token_version），会员侧没抄。后果：后台停用/封禁一个会员后，对方手里的 token 仍可畅通 30 天 —— 付费墙侧同样只看 plan 不看 status，停用会员照样能读正文。

修法：

① 提取器加回查 — MemberAuth 加 AppState: FromRef<S> 约束，按请求查 members.status，status != 1 或查不到 → 401。
② 付费墙侧同步收紧 — MemberGate 查询补上 status 字段，新增 active()；subscribed()、invite 分支与兜底分支全部改为「active() 才放行」。停用会员在付费墙侧统一返 402，不泄漏正文。

5过程中踩到并解决的坑（下次直接省掉）

坑 1（最关键）· Turso 后端把唯一键冲突吞成 Ok(0)，不是 Err

Webhook 幂等最初用 inserted.is_err() 判冲突。SQLite 路径下唯一键冲突确实返 Err，测试通过；但切到 Turso 路径（本地 shim）实测时，冲突表现为 Ok(0) —— is_err() 为 false，于是 重复事件被当成首次处理，库里只有 1 行、副作用却跑了两遍。这正是「重复投递导致重复发货」的典型资损形态。

修法：新增 fn insert_ok(written: &Result<u64, DbErr>) -> bool { matches!(written, Ok(n) if *n > 0) }，并写单测钉死 Ok(0) → 冲突。结论：在这个项目里判「有没有写进去」一律看 rows_affected > 0，不要只看 is_err()。
注意类型：这里的 DbErr 是 crate::cmsdb::DbErr（本地 pub struct DbErr(pub String)），不是 sea_orm::DbErr。写签名时别用错。

坑 2 · bash 内联 Python 里的反引号会被当命令替换

用 bash 内联 python -c "..." 给 Rust 注释补写含反引号的文字（如 `CmsDb::exec_tx`）时，反引号被 shell 优先解析成命令替换，导致写进源码的注释残缺（出现 不能用 判定 这种断字）。

修法：涉及反引号 / $ 的内容改用独立 .py 脚本文件执行，不写在 bash 内联字符串里。复查后 0 处破损。

坑 3 · 编译中断后启动到旧二进制，迁移没落库

cargo build 中途因 FromRef 报错中断，只编出了 test profile；taskkill 后启动的仍是改动前的旧 exe（时间戳早于本次修改），表现为「webhook_events 表不存在」「P0-1 仍可打通」——看起来像修复失效，实则是跑错了二进制。

修法：重新完整构建后核对 exe 生成时间，再启动；并直接查 _migrations + pragma table_info 确认迁移落库，不要只凭接口行为反推。
