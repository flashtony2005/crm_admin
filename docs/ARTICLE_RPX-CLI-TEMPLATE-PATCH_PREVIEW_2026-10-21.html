rpx template：像改代码一样改报表定义

定义即代码，那就要能像代码一样改

报表定义是一份 JSON 文件。既然是文件，就该能查看、能校验、能套模板新建、能打补丁——像改代码一样改它，而不是只能靠某个编辑器点来点去。

rpx template 提供四个动作：inspect（看）、validate（校）、create（建）、patch（改）。改完要过lint、再run。

rpx template 的四个动作分别是：配上 rpx schema，就构成了一个不依赖图形界面的完整编辑闭环。

inspect：看模板里到底写了什么

最常用的一条。它把模板 JSON 摊成「按地址组织」的形式，比直接读原始 JSON 好懂得多：

rpx template inspect payroll.json

返回三部分：grid（行列数）、datasets（数据集声明）、items（逐格）。每一格给的是：

{
  "address": "A1",
  "json_pointer": "/cells/0",
  "definition": { "row": 1, "col": 1, "text": "员 工 工 资 表",
                  "extend_mode": "none", "font_size": 18, ... },
  "left_head": { "state": "inferred_at_run" },
  "top_head":  { "state": "inferred_at_run" }
}

三个字段值得说：

  • address：A1 风格地址，坐标从 1 起。看定义时用地址比用行列号直观。
  • json_pointer：如 /cells/0。这是给 RFC 6902 补丁用的——你要改哪一格，path 就写这个。
  • left_head / top_head 的 state：inferred_at_run 表示主格关系要等运行时才推导出来，定义里没写死。想知道扩展结构，看这里。

只想看一格？加 --cell A1。格子多的时候用 --limit / --offset 分页（每页上限 500）。

validate：结构成不成立

rpx template validate payroll.json

实测返回：

"checked": ["schema", "declared_heads", "unconditional_scalar_cycles",
             "formula_preparation", "parameter_binding", "inferred_heads"],
"deferred": ["data_loading", "calculation", "pagination", "export"],
"valid": true

它回答的是「这份定义能不能被引擎接受」：schema 对不对、声明的主格关系有没有环路、公式能不能完成准备、参数能不能绑定。

注意 deferred 那四项和 lint 完全一样——取数、计算、分页、导出都不在离线校验范围内。validate 通过只说明结构合法，不说明产物正确。要拦「不报错但产物错」的写法，得再跑 rpx lint（这篇专门讲它）。

还有一个可选开关：--probe-data。带上它，validate 会顺带探一下数据，把「列名不存在」这类问题提前暴露出来，而不用等到 run。

create：从内置示例起步

不想从空文件写起，就用内置示例。当前有 5 个：

id名称
grouped-sales区域分组销售
complex-master复杂主格经营分析
multi-column多栏报表
chart-gallery统计图集
images图片与背景
rpx template create --example grouped-sales --out-dir my-report

实测它会在目标目录里放两个文件：template.json 和 sales.csv——也就是一份立刻能跑的完整包，不是只有模板还得自己去找数据。

这正是「定义即代码」想要的起步体验：复制一份能跑的，再改成你自己的。不知道有哪些示例，rpx catalog examples 会列出来。

patch：用 RFC 6902 改定义

这是最适合自动化的一环。补丁是标准 RFC 6902 JSON Patch，通过 --patch-file 传入：

[{ "op": "replace", "path": "/cells/0/text", "value": "2026 年 9 月工资表" }]
rpx template patch payroll.json \
    --patch-file patch.json --out patched.json

实测打完之后，patched.json 里 cells[0].text 确实变成了新标题，其余部分不动。

--dry-run：先看效果再落盘

rpx template patch payroll.json --patch-file patch.json \
    --out patched.json --dry-run

返回 dry_run: true 并把补丁后的完整模板回显出来，但不写文件。这一步很值得养成习惯：补丁里的 path 写错是常事，dry-run 能让你在落盘前看到「改完长什么样」。

补丁无法应用会返回 PATCH_INVALID（退出码 3），不会给你一份半改的文件。

--out 不会覆盖已存在的文件。实测再跑一次同名输出会直接报 IO_ERROR（「文件存在」，os error 80）。这和 run --out-dir 拒绝已存在目录是同一套策略：引擎不替你决定要不要覆盖。脚本里要么每次换新文件名，要么先删。

为什么用补丁而不是直接改 JSON？

直接读写 JSON 当然可以，但补丁有三个好处：

  • 可审计：补丁文件本身就是「改了什么」的记录，能进版本库；
  • 可复现：同一份补丁对同一份模板，结果一致；
  • 可回退：原模板不动，输出是新文件（--out 指定）。

schema：给编辑器接上补全

rpx schema template

输出内置的 JSON Schema（draft 2020-12，additionalProperties: false）。把它配进 VS Code 之类支持 JSON Schema 的编辑器，写定义时就有字段补全和拼写校验——字段名写错会在编辑时就被标红，而不是等到 validate 才报。

注意 schema 只覆盖结构和类型；表达式语法、语义约束是由引擎的定义加载器另外检查的（schema 描述里也写明了这一点）。

四条命令怎么串起来

一个典型的「改一份报表」回路：

  1. rpx template inspect —— 找到要改的格子和它的 json_pointer；
  2. 写补丁文件（path 用上一步的 pointer）；
  3. rpx template patch --dry-run —— 确认改对了；
  4. rpx template patch —— 落盘；
  5. rpx lint → rpx run —— 自检再真跑。

全程不需要打开任何图形界面，也每一步都可以被脚本或 Agent 执行——这是「定义即代码」真正的意思：不是「用 JSON 存配置」，而是让报表能进版本库、能走评审、能被自动化。

常见问题

inspect 和 result inspect 有什么区别？

对象不同。template inspect 看的是定义（你写了什么），result inspect 看的是结果（算出来是什么）。后者的输入是 run 产出的 result.json，每格带 origin 指回模板原格。

patch 能改数据集吗？

能。数据集是 /datasets/0/file/file_name 这样的路径，同样用 json_pointer 定位。rpx lint 报 L005 / L006 时给的就是这类 pointer，可以直接拿去写补丁。

validate 通过了，为什么 run 还是失败？

因为 deferred 那四项（取数、计算、分页、导出）validate 不管。最常见的就是列名对不上——模板里写 ds1.sum(amount)，数据里那列其实叫 amt。这种问题要么用 --probe-data 提前探，要么先跑 rpx dataset inspect 看真实列名。

内置函数有哪些？

rpx catalog functions，实测返回 20 个：13 个通用函数加 7 个数据集聚合函数（ds.sum / ds.avg / ds.max / ds.min / ds.count / ds.group / ds.select）。每个都带 signature、example 和 limitations——比如 sum 会注明「区域聚合；数据集聚合使用 ds.sum(expr[,filter])」，两者不要混用。
